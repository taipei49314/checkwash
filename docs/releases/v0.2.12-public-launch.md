# checkwash v0.2.12: public launch and first use

Prepared 2026-09-06. **Alpha; the [1.0 criteria](../stability.md#what-must-change-before-10) are not met.**

checkwash flags known patterns of weakened verification in a Git diff. It runs
locally, uses no LLM or network during analysis, and never executes the code
under review. A passing result means no configured blocking finding was found;
it does not establish that a change is correct or honest.

## Try it on a change you understand

Start in a disposable virtual environment with Python 3.11 or newer and Git:

```bash
python -m venv .venv
# Activate .venv using your shell's usual command, then:
python -m pip install checkwash==0.2.12
checkwash --version
checkwash check HEAD~1..HEAD
checkwash check HEAD~1..HEAD --format json
checkwash check HEAD~1..HEAD --format sarif
```

Run the checks inside your repository. The example needs two available
commits; choose an existing range if your history differs. For a PR, use the
actual base and head with `checkwash check BASE...HEAD` (the three-dot form
compares the merge base with HEAD).
Review findings against the diff before adding enforcement. Keep your normal
tests and human review in that process.

The exit contract is **0 pass / 1 block / 2 engine error**. Capture the process
exit code as well as output. An invalid revision can return exit 2 with a
human-readable error on stderr and **no JSON on stdout**, even when JSON was
requested. The [stability page](../stability.md#machine-findings-contract-findings_version--ir_version)
describes the actual `checkwash_*` JSON keys and the pre-rename compatibility
exception.

When ready to enforce a verdict, follow the [required-check workflow](../../README.md#required-check--the-only-configuration-that-blocks-a-merge)
and require the **`checkwash`** status context. Record the Action version you
deployed. `checkwash doctor` checks local configuration; its success does not
verify live branch protection. Confirm that separately in repository settings.
The [enterprise checklist](../enterprise.md) covers reviewed exemptions and
protection of both supported configuration directories.

## Invitation from the author

I'm looking for developers willing to try checkwash on a Python repository
they know. Start with a change you have already reviewed and tell me whether
the findings are useful, noisy, or hard to understand. It is v0.2.12 alpha:
known gaps and a substantial honest-refactor cost remain. A useful trial does
not need an endorsement or an immediate required-check rollout.

If you choose to share feedback, include the installed version and surface,
Python/OS, the exit code, what you expected and what checkwash reported. Share
only repository material you are comfortable making public; a description is
enough to start. Use [issues](https://github.com/taipei49314/checkwash/issues)
for ordinary feedback and [SECURITY.md](../../SECURITY.md) for security reports.

## Release boundary and next work

Public availability does not satisfy the 1.0 acceptance review. Independent
adoption evidence, agreed precision thresholds and the scoped disposition of
known failures are still needed. The adoption cohort numbers in stability
are a proposal for that review, not a prerequisite for trying this alpha.

Next quarter's main engineering work is reducing **honest-refactor false
positives**, with agreed tradeoffs before detector changes and separate
measurements of review/exemption workload. The existing frontend candidates
and catalog decisions retain their own review process. This documentation
package does not merge them or reissue v0.2.12.
