# v0.8.0: release evidence and limits

Prepared on 2026-10-15 from `main` at
`cdd74e0e2d3428d6dd747f35b0b0928526335fa5`. Publication: `<to be recorded>`.
A separate publication verification record will add the actual tag, packages,
PyPI and visitor checks once they exist. Until that record is complete this
guide describes a candidate, and the README keeps installing v0.7.0.

On 2026-10-15 the maintainer authorized this release (「這版要先發了」) and
set its scope to `main` as it stood at `cdd74e0`: the 25 pull requests merged
since v0.7.0, #370 to #453. #421 moves to a later minor release, and #456 is
a known issue. The maintainer also chose to publish first and run the
acceptance sweeps on the EC pool afterwards, so this release's false-positive
cost is not measured (see "Limits that remain"). The one-time scope is
recorded in [RELEASING](../RELEASING.md).

This is a minor release because one frozen contract changes:
`check --format hook-json` now exits 0 on an engine error (#414). The finding
JSON shape (`checkwash_findings_version: 2`), `IR_VERSION` 2, the rule IDs,
the severity model and the fingerprint scheme are unchanged.

## What changes

Each item names its issue and pull request. For the rounds #439 to #453, the
SPEC, THREATMODEL and DECISIONS text the maintainer approved on 2026-10-15
holds the exact boundary; [known issues](../KNOWN-ISSUES-v0.8.0.md) lists
what remains.

### Security

- **The Action no longer runs code from the pull request it judges** (#372;
  advisory #413). Every published Action up to and including v0.7.0 ran
  `python -m pip` and then the first `checkwash` on `PATH`, with the pull
  request's checkout as the working directory. A module in that checkout,
  such as a top-level `pip` package, could replace the installer and then the
  checker. The v0.8.0 Action takes the interpreter from setup-python, installs
  its own pinned source into a private environment under `RUNNER_TEMP`,
  checks the installed files and version against that source, fixes the base
  and head refs before analysis, and runs the engine in isolated mode. BLOCK
  and ERROR stay failed steps, raw output cannot issue workflow commands, and
  the `comment-pr` token reaches only the comment helper. The interpreter,
  shell startup, runner image, PyPI build tooling and setup-python remain
  trusted; an earlier step in the same job that ran pull-request code can
  still compromise the runner.
  [Advisory](../../SECURITY.md#known-issue-action-trust-boundary)
  · [Action reference](../../action/README.md)
- **The quality preview Action gets the same isolation** (#375). It reuses
  the verified private runtime. Its six outputs, three-dot range and
  base-owned policy are unchanged.

### Behaviour changes you will notice

- **An engine error in the Claude Code Stop hook no longer blocks the stop**
  (#414, #447). With `check --format hook-json`, an engine error, and a config
  or allowlist parse error under `on_engine_error = "block"`, exit 0 and print
  a JSON `systemMessage` that begins `checkwash: this change was not analysed,
  so it was neither passed nor blocked.` and names the error. The payload has
  no `decision`, so the agent may stop and the user sees why. v0.7.0 exited 2.
  Every other format, including the pre-commit hook's term output and the
  Action, still exits 2, and a malformed range is still a usage error with
  exit 2 in every format. The hook is an author-side check; the required CI
  check remains the gate. An agent can provoke such an error on purpose
  (#456, known issue).
- **Commands run from a subdirectory read the repository from its root**
  (#416, #453). When `--repo` (by default the current directory) is a
  subdirectory, `check` and `sweep` ask Git for the root, analyse the whole
  repository and print one stderr line:
  `checkwash: using the repository root <root>, not its subdirectory <prefix>`.
  The line also names any `.checkwash/` or `.greenwash/` directory between the
  invoked directory and the root as not read; only the root's apply. stdout
  and the exit code equal those of the same run at the root. If the root
  cannot be resolved, `check` and `sweep` report an engine error. `allow`,
  `doctor` and the `quality` forms that read a repository re-root the same
  way, and use `--repo` as given when Git cannot answer; `allow` now writes the
  root's ledger. `hook install`, `quality profiles`, `quality explain`, `bench`
  and `demo` are unchanged. `--task` is mapped lexically through Git's prefix.
  From a subdirectory, a task file that the base tree does not hold at the
  mapped path is an engine error; the untracked fallback is kept at the root
  only. From a subdirectory v0.7.0 mostly stopped with engine errors, `doctor`
  reported a false FAIL, and `allow` wrote a ledger that `check` never read.
- **Oversized files that no detector reads no longer stop the run** (#415,
  #448). This fixes the v0.7.0 regression in which any changed side over
  1,000,000 bytes, or a root `uv.lock` or `poetry.lock` that large at the base,
  made the run exit 2 without naming the file. Such a side is now carried
  unread: its change earns no findings and no repair evidence, and `check`
  prints `checkwash: not read, over the source byte limit: <path> (<side>,
  <size> > 1000000 bytes); it earns no repair evidence` on stderr. A path a
  detector must read still stops the run with exit 2, now naming path, side,
  size and limit, for example `strict snapshot source exceeds the byte limit:
  tests/test_big.py (head, 1200000 > 1000000 bytes)`. Must-read paths are
  test, conftest, CI, guardrail and snapshot files, JS/TS tests and setup
  files, runner-shaped files and test-command manifests, any `.py` module whether
  added, deleted, renamed or edited, any pytest configuration at any depth,
  any file with no extension, any non-generated file under the root
  `scripts/`, and paths outside `scope.allow`. An oversized root `poetry.lock`
  or `uv.lock` at the base is skipped with a note (`sweep` skips it silently);
  a root `pyproject.toml` or `requirements*.txt` that large still stops every
  run.
- **Directory symlinks in the working tree** (#414, #447). Without a range,
  `check`, as the pre-commit and Stop hooks run it, exited 2 on any `.py` edit
  when the working tree held a directory symlink, even a gitignored
  `.venv/lib64 -> lib` or pnpm's `node_modules`, and named no path. A directory
  symlink is now listed as an opaque directory, as a submodule is, and never
  followed. A read inside it, an import that resolves into it or a pytest
  collection that can reach it fails, naming it. pytest's default
  `norecursedirs` keeps `.venv` and `node_modules` out of reach, so those
  trees give a verdict. The working-tree searches and the 200,000-path limit
  refusal now name the path.

### Detection changes

These newly block at high. Their false-positive cost has not been measured.

- **conftest code that forces pytest's exit status** (#422, #450).
  `exitstatus` writes on any receiver, zero, decrementing or unreadable
  `testsfailed` writes, `pytest.exit(returncode=...)`, `os._exit`, `sys.exit`,
  `exit()`/`quit()` and `SystemExit`, in a conftest's hooks, fixtures and
  their finalizers, `atexit` callables, module scope or the same-file
  functions these call, are a runtime control. It is reported as
  `TEST_DISABLED` with a `conftest.runtime.exit.<place>.<effect>.<path-hash>`
  marker on `<suite>`. It carries no guard, so neither a compatibility gate
  nor repair evidence holds it. Values are read modulo 256; 0, 5 and
  unreadable values count. The hook's own unchanged status, and the common
  `pytest_sessionfinish` recipe that turns exit 5 (no tests collected) into
  0 when the status provably equals 5, do not count.
- **conftest no-op replacements of what pytest runs** (#432, #452). A no-op
  written to `item.runtest`, `item.obj` or `item._obj` on the item parameter
  of a listed hook, to `runtest` on pytest's item classes (`pytest.Function`,
  `pytest.Item`, `_pytest.python.Function`,
  `_pytest.unittest.TestCaseFunction`), or to a native `unittest.TestCase`
  method from a fixed list (its assert and fail methods, `_callTestMethod`,
  `run` and others) at module scope or in a top-level `pytest_*` function, is
  a runtime control reported as `TEST_DISABLED`. Only a lambda or an
  undecorated same-file function is read as the replacement. An import inside
  a hook that may not run, and `from builtins import setattr`, no longer hide
  #84's report rewrites.
- **An always-passing assertion no longer excuses a JS/TS catch** (#431,
  #449). A new catch that swallows a supported synchronous assertion is
  reported as `BROAD_EXCEPT_ADDED` even when the catch holds an assertion the
  frontend proves always passes (a resolved Vitest/Jest `expect`, node:assert
  or chai `assert` call with a `true`, `false` or `null` operand, matching
  predicate and polarity, and no extra arguments). Its evidence text is
  `catch always-passing assertion`. An always-failing assertion such as
  `expect(true).toBe(false)` still counts as inspection.
  [Catch boundary](../js-catch-swallowing.md)

### Fixes: runs that stopped with exit 2 now give a verdict

- **Deep binary expressions** (#374). A valid assignment of about 350 binary
  terms could raise `RecursionError` while building binding keys. Only a root
  binary operation that fails the standard unparser is retried iteratively;
  every result the standard library produced before is kept.
- **Long string concatenations** (#441). A module-level
  `NAME = "a" + "b" + ...` of thousands of terms made parsing, dumping or
  tracing raise `RecursionError`. Complete top-level lines of that shape are
  rebuilt from tokens with exact positions; any other deep shape keeps the
  original error.
- **Large test files in the stand-in pass** (#345, #439). Its node limit rises
  from 30,000 to 200,000, so the 1,000,000-byte limit binds first on ordinary
  code. Byte and node limit errors name the path, side, count and limit.
- **Symlinked and dormant pytest configs** (#346, #442). The runtime-provider
  pass no longer reads, up front, a nested pytest config whose directory holds
  no test file on either side. In a range check, a recognized pytest config
  name that is a symlink to a regular file of the same commit reads as that
  file. Other links fail closed, and nonregular-source refusals name the
  path. [Subject integrity](../subject-integrity.md)
- **Nested inline JS callbacks** (#386). The inline callback inventory no
  longer rescans each nested call, which had broken the existing scaling
  budget at depth 80. Parsed output is unchanged.

## Upgrading from v0.7.0

- **Allowlists.** The fingerprint scheme is unchanged, and no existing test or
  fixture expectation changed except one hook-runtime exit expectation that
  follows #414 (#451, owner-approved). Entries recorded on v0.7.0 are expected
  to keep matching; this comes from the pull requests' review and CI, not from
  a sweep. The new findings above carry new fingerprints. An entry written by
  `allow` from a subdirectory on v0.7.0 went to a ledger under that
  subdirectory, which `check` never read and still does not; a run from that
  subdirectory now names the directory on stderr as not read. Review such
  entries and record them again from the root. #421, planned for a later
  minor release, will move the assertion-level namespaces to content-bound
  identities; entries for those rules will then need to be recorded again.
- **Stop hook.** If you relied on exit 2 from the Stop hook to keep an agent
  working after an engine error, it no longer does. Treat a "not analysed"
  message as a check that did not run, and keep the required CI check.
- **Runs that used to error.** Runs that stopped with exit 2 on v0.7.0 because
  of an oversized side no detector reads, a directory symlink, a deep
  expression, a large test file, a symlinked pytest config or a subdirectory
  can now pass or block. A pass with an unread side exits 0 like a full pass;
  only stderr names the side (#454). Keep stderr with every result.
- **Messages.** Size refusals name path, side, size and limit under the
  generic prefix `SourceOverLimit:`. Outside Git, or with a missing `--repo`,
  the engine error of `check` and `sweep` names
  `git rev-parse --is-inside-work-tree` instead of the first Git call that
  failed before. Each of these commands starts one more Git process at the
  root and two more from a subdirectory.
- **Action callers.** After the publication checks pass, a reviewed follow-up
  on `main` advances the README's CLI commands, `release/advertised.toml` and
  the recommended Action to v0.8.0, at commit `<to be recorded>`; since
  2026-10-14 the Action recommendation no longer lags one release. A CLI
  upgrade does not change an Action pin: edit the `uses:` line yourself. The
  v0.8.0 Action needs setup-python in the same job (it reads `pythonLocation`,
  or the new `python-path` input, and never falls back to `PATH`), Python
  3.11–3.13, a checkout with `fetch-depth: 0` in which both refs exist, and a
  dedicated job that runs no pull-request code before the check. It adds the
  outputs `exit-code`, `receipt-path` and `identity-path`. The README snippet
  already meets these requirements. The quality preview Action needs
  setup-python or `python-path` in the same way.
- **doctor.** At `cdd74e0`, `checkwash doctor` still accepts only the Action
  commit built into it, the v0.6.0 commit `8c70efbf`. A workflow pinned to the
  v0.8.0 Action is reported as "workflow analysis incomplete" with an
  unsupported SHA. This is a warning, not a failure (known issues).

## Use it and preserve the result

Use Python 3.11 or later and Git. After the publication record verifies the
release asset, download
[checkwash.pyz](https://github.com/taipei49314/checkwash/releases/download/v0.8.0/checkwash.pyz)
or install `pipx install checkwash==0.8.0`, and try a change you understand:

    python checkwash.pyz --version
    python checkwash.pyz check BASE..HEAD --repo /path/to/repository --format json

Exit 0 passes the configured gate, exit 1 blocks, and exit 2 is an input or
analysis error; with `--format hook-json` an engine error exits 0 with the
"not analysed" message. Retain stdout, stderr and exit status. Stderr is the
only place that names a side checkwash did not read. A pass does not prove a
change correct or honest; warnings, skipped files and unread sides still need
review.

## Limits that remain

- **Acceptance sweeps.** The acceptance sweeps of #345, #346, #414, #415,
  #416, #422, #431 and #432, and the corpus sweep, have not run:
  `NOT_RUN：工作機規則（POLICY work-machine-local），the owner chose to release first and run them on the pool after publication`.
  So neither the false-positive cost of the new blocks, nor how many of
  v0.7.0's 54 added pass-to-error pairs this release recovers, nor its cost on
  the fixed Python and JS/TS sets is measured. RELEASING requires the corpus
  sweep when a round changes detector behaviour; it is outstanding, not
  waived. Those issues stay open until their sweeps and texts land.
- **Held-out and JS/TS measurement.** No held-out measurement exists. EC T-528
  closed as CANCELLED on 2026-10-14, with its six held-out candidates
  UNVERIFIED. The JS/TS false-positive cost remains unmeasured (#212).
- **Open reports.** The open P1 reports this release does not address, and
  the residuals of each round, are in
  [known issues](../KNOWN-ISSUES-v0.8.0.md). Among them is #456: a must-read
  file padded past the size limit turns a Stop-hook block into the
  non-blocking "not analysed" message.
- **1.0.** The 1.0 criteria remain **NOT MET**: adoption, refactor cost and
  known low-cost failures still lack the required evidence
  ([criteria](../stability.md#what-must-change-before-10)). This release does
  not move them.

Checkwash remains alpha. A pass does not prove correctness or honesty. This
one-time publication authorizes no downstream re-pin and no other release.
