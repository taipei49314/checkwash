# Checkwash 0.11.0: an edit-time ask for Claude Code, failure relays and the release's own Action pin

Status, 2026-11-03: **release candidate, not published**. The release pull
request carries this guide; the publication record follows the release
stages and the checks of the public files. Until then the README's install
commands and Action pin name v0.10.0.

0.11.0 carries the changes D-189 to D-196 of [DECISIONS](../../DECISIONS.md)
record. Nelson approved its scope item by item from 2026-10-28 to 2026-11-02,
and each of those entries quotes his words; D-190, D-191 and D-194 quote his
2026-10-28 answer in full. The findings document stays at version 2 and the IR at version 3.

## Claude Code hooks (D-189)

- **A PreToolUse ask.** `checkwash hook install --agent claude-code` now
  adds a PreToolUse handler. When an Edit, Write or MultiEdit of a Python
  test file would leave a finding of `ASSERT_WEAKENED`, `ASSERT_REMOVED`,
  `TEST_DISABLED`, `TOLERANCE_LOOSENED` or `BROAD_EXCEPT_ADDED` at high, with
  `oracle_freeze` forced, the hook asks you before the edit is made. In a
  `claude -p` run nobody can answer, so such an edit is denied. One
  pre-registered lifecycle receipt exercised it, in `-p` mode only; the
  interactive prompt is not verified in any mode.
- **A local install by default.** The hooks go to
  `.claude/settings.local.json`; `--shared` writes `.claude/settings.json`,
  with no PreToolUse handler. A script that installed shared settings with
  no flag must now pass `--shared`: with neither flag, a repository whose
  shared settings already hold the managed Stop or SessionStart handler
  makes the install exit 2.
- **A Stop block that reports.** The block reason no longer offers a
  `checkwash allow` command: it tells Claude to fix the production code or to
  report the finding to you, and since D-191 it quotes a weakened or removed
  assertion's source text. A continuation stop on the same blocking set is
  released with a note instead of being blocked again.

Both hooks are author-side checks; the required CI check remains the gate.
What they do not cover is in [KNOWN-ISSUES-v0.11.0](../KNOWN-ISSUES-v0.11.0.md).

## Verdict changes

- **Failure relays (D-190).** A broad `except` in a Python test that hands
  the failure unchanged to an asyncio future the test awaits, as uvloop's
  regression tests do, is no longer counted as an added swallow, within the
  bounded shape SPEC §4 reads. 0.10.0 blocked the three uvloop inputs that
  D-187 accepted as known costs for 0.10 only; the diagnostic below runs them
  again.
- **#419 (D-191).** #419 closes as a documented residual of E1's repair
  evidence, not a fix: a weakened Python or JS/TS test beside an edit that
  changes nothing can still pass at the default threshold. What still passes,
  what blocks and how to block the rest are in the known issues and the
  [enterprise checklist](../enterprise.md#7-hardening-against-bought-repair-evidence-419).
  Nelson chose this residual for 0.11 on purpose, and 0.12 is to change it
  ([D-196](../../DECISIONS.md)).
- **`pytest.raises` folds and parametrize cells (D-192).** After an outside
  report on #130, a lone `pytest.raises` carrier folded into a literal
  `parametrize` table is proved like an assertion, so an honest fold can keep
  its credit. Separately, a test file that lost units but no oracle mass can
  be a D5 candidate when a live unit arrived in it. A test whose parametrize
  cells never reach it as written gets no assertion keys, so such a fold or
  move now blocks at high unless the complete unit moved unchanged.
- **Collection settings (D-193).** A moved or folded Python test pays for the
  test it replaces only where the repository's own pytest configuration
  certainly collects it, and a rename out of that collection is a
  disappearance. Where checkwash cannot read the selection (a `-k` in
  `addopts`, for example), no Python move or fold earns credit.

## `doctor` and the Action pin (D-194, D-196)

A release cannot name its own commit. From 0.11.0 the release pull request's
last commit changes one line, `doctor`'s own Action pin, to the commit before
it, and after publication the README recommends that commit,
`v0.11.0^2^1`, not the commit the tag points to. `doctor` 0.11.0 accepts two
exact Action pins: v0.10.0's and its own. `doctor` 0.10.0 rejects the 0.11.0
pin, so upgrade the CLI and its local hooks before the Action pin. Pin
updaters such as Dependabot and Renovate will propose the tag's commit, which
`doctor` rejects, and zizmor's `ref-version-mismatch` audit can report the
pin's comment (inferred from those tools' documentation, not run). Nelson
accepted these consequences with documentation for 0.11, and 0.12 is to point
the tag at the recommended commit. Verify the pin in a clone:
`git -C checkwash diff 'v0.11.0^2^1' v0.11.0` shows one changed line, in
`src/checkwash/doctor.py`.

## checkwash's own tests (D-195)

Five test relaxations that agent sessions had left in checkwash's own tests
are restored. This changes no engine behaviour.

Separately, one case of a #455 test, which runs only where it can create
symlinks and so is skipped on Windows without the symlink privilege, still
expected the working-tree refusal message from before v0.10.0 and failed on
Linux. It now expects the current message; the engine is unchanged.

## The three uvloop inputs (D-176, D-187)

D-187 accepted, for 0.10 only, three uvloop regression-test additions that
0.10.0 blocks: each relays an assertion failure from a callback or a thread
to an asyncio future that the test awaits. A separate run of the same script
and engines checked them again, each against its original first parent:

| uvloop commit | v0.10.0 | 0.11.0 candidate |
|---|---|---|
| `7b202ccf644396a4ae8ff8053578058f5023ac63` | block, one HIGH `BROAD_EXCEPT_ADDED` | pass, no finding |
| `2081db8927dc2d3a66b7c8d7aa317d71aba198f9` | block, one HIGH `BROAD_EXCEPT_ADDED` | pass, no finding |
| `9cba7493a152e5a77bbde9a32143d84433d1cd3d` | block, two HIGH `BROAD_EXCEPT_ADDED` | pass, no finding |

D-190 reads these relays, so the three costs D-187 accepted for 0.10 need no
acceptance for 0.11.0. D-187 also accepted, for 0.10 only, D-176's explicitly
unmeasured remaining-history risk: an honest broad `except` that D-190 does
not read still blocks beside an opaque production change, and neither run
measures how often history holds one. Claude accepts that risk for 0.11.0
only, as a delegated decision ([0.11.0 disposition](../d176-cost-disposition-0.11.0.md)).
This reads three commits; it does not run uvloop.

## Evidence and scope

Each release stage (pull request, main, tag, release event and public
visitor) is collected afresh on LAPTOP-01AGNPJU, Windows, CPython 3.11.9,
`HUMAN_AUTHORIZED_LOCAL_PJU_NOT_EC_POOL`, one route for the whole chain, as
for v0.10.0. Native Linux, macOS and other Python versions are NOT_RUN for
the release receipts; a separate six-leg PJU batch (Windows and Linux in
Docker, Python 3.11 to 3.13) is supplementary evidence, not a release
receipt, and its result is recorded with the release. Source, wheel and pyz
agreement is not an unexecuted platform comparison.

The public installation manifest and the README pins advance only after the
public files are verified. **1.0 readiness remains NOT_MET**: these in-sample
comparisons establish no held-out rate, adoption cohort or unexecuted
platform coverage, and Nelson's stop before 1.0 remains in force.
