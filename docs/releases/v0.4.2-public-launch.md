# v0.4.2 release guide

The maintainer approved this bounded release plan on 2026-09-23. Estate
T-449 records the one-time scope, following the JS/TS foundation in
[PR #167](https://github.com/taipei49314/checkwash/pull/167). The
[GitHub Release](https://github.com/taipei49314/checkwash/releases/tag/v0.4.2)
is the publication record: it identifies the final source, completed remote
checks and public artifact hashes. Preparation or a temporary runner tag alone
does not mean the version is published.

## What changes

Inline test callbacks own their assertions, including nested tests. Assertions
outside a callback and inside unused helpers or default parameter expressions
cannot replace a deleted assertion in that test. Complete matcher arguments
reach existing detectors: `toBe(42)` changing to `toBe(0)` can report
`EXPECTED_VALUE_CHANGED`, and `toBeCloseTo(5, 4)` changing to precision `1`
can report `TOLERANCE_LOOSENED`.

Equivalent scalar spellings, such as `42` and `4.2e1`, remain equivalent when
existing detectors compare the expected value. This prevents formatting-only
substitution reports and keeps equivalent spellings from hiding subject
normalization or input changes. Unknown values retain their conservative
handling; Python behavior is unchanged.

The bounded model covers finite Number literals, quoted strings, booleans and
`null`. Node expected-value evidence applies to explicit `strictEqual` and
`deepStrictEqual`. Positive `toBeCloseTo` precision covers explicit integers
from -308 through 307 and the default of two digits. Objects, arrays, BigInt,
non-finite numbers, arbitrary expressions and negated precision are not given
the same value/weakening proof. See [assertion coverage](../assertion-coverage.md).

This is not a general JS/TS parser or execution model. Direct inline callbacks
retain lexical coverage without proving that a callee executes them. General
helper execution, suite/table collection, async completion and JS/TS production
repair evidence remain outside this release. Typed return annotations on renamed
Node test-context callbacks can still leave context assertions unresolved;
coverage diagnostics and an apparently passing verdict do not establish full
assertion coverage.

Existing finding/IR schemas, severity and exit-code contracts are unchanged.
Established Jest/Vitest finding fingerprints remain compatible. No frozen fixture
label, strength lattice, alignment parameter or performance gate is relaxed.

## Evidence and limits

Final qualification binds the complete test suite, self-check, source/wheel/pyz
assertion contracts, actual-tag nine-platform CI and corpus byte comparison to
their exact source. The original assertion inventory and the separately extended
foundation inventory retain independent preserving and loss controls.

The release also records two separate history measurements:

- The fixed 1,800-commit corpus from six Python projects checks regression
  behavior. Its historic stored sweeps and human adjudication are not overwritten.
- A finite JS/TS sample is selected and reviewed before engine replay, with
  exact repository/commit/parent/path and file hashes. Preserving, ambiguous and
  loss cases have separate denominators. File-level replays omit other changes
  in the original commits; their outcomes do not establish whole-commit intent,
  full syntax coverage or a general false-positive rate.

The public release record links complete receipts and any remaining gaps. Old
results are not relabeled as measurements of the final release. Human product
acceptance remains separate from mechanical qualification.

Under the one-release trust lag, the recommended Action advances to **v0.4.1**,
commit `ea726c9cbd172b838bcf42b2c9969759e4ca358e`. It includes the Node assertion
repair and coverage diagnostics, but not this foundation. Its engine is measured
separately against the current assertion contract; real misses remain visibly
failed. The frozen legacy v0.3.3 quality comparison also retains its disclosed
cross-version mismatch. Neither measurement substitutes for or weakens the
required same-source release checks.

## Try it on a change you understand

With Python 3.11+ and Git, after publication:

```sh
pipx install checkwash==0.4.2
checkwash --version
checkwash demo
checkwash check HEAD~1..HEAD --format json --coverage-report coverage.json
```

Exit 0 means no blocking finding, exit 1 means a blocked change, and exit 2 means
an analysis/input error. GitHub provides the offline `checkwash.pyz`; the wheel
and sdist are also published through the existing PyPI workflow. The release
record verifies downloaded artifact hashes and version/demo behavior remotely.

Checkwash remains alpha. A pass does not prove correctness or honesty. This
one-time publication does not authorize another release or a downstream-repository
pin update.
