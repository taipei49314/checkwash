## Repair evidence refused to weakened tests (D-199)

0.11.0 closed #419 as a documented residual: an edit that changes nothing,
such as `+ 0` in a function a test calls or one line in a template, could
hold a weakened test at warn, which passes at the default threshold. Nelson
chose to change that in 0.12 ([D-196](../../DECISIONS-archive-4.md)), and
chose the option D-199 implements.

- **In a Python test or conftest** (any `.py` file), a weakened, removed,
  skipped or loosened assertion, a broad `except`, a stand-in for the code
  under test (`TEST_PATCHES_SUBJECT`, `CONFTEST_PATCHES_PROD`, and an
  import shadow wherever it is reported), a normalized subject, a changed
  subject input and an expectation derived from the input take no repair
  evidence. **In a JS/TS test**, a weakened or loosened assertion, a broad
  catch, a skip added to a live test, and a table left with no row to run
  take none.
- Each such finding blocks beside any production change, a no-op one
  included, unless something other than repair evidence holds it: a
  compatibility `skipif` (D6), a mild weakening inside the exact family
  (D7), a deletion beside a removed symbol (D8) and the other compensations
  still apply. A finding that a production change reached is labelled
  `REPAIR_EVIDENCE_REFUSED`.
- **It blocks honest changes too:** a deprecated API removed with an
  assertion on it, a test rewritten beside a behaviour change, and an
  optional-dependency skip added beside the change that needs it. Each
  needs a reviewed exemption.
- **Still passes by default:** a rewritten expected value or a substituted
  assertion beside a no-op edit, a weakening respelled as one of them, a
  test deletion that a renamed private symbol escorts, and in JS/TS a
  removed assertion or test, deleted parametrize rows, a test parked in
  dead code and a stand-in or subject change. The
  [known issues](../KNOWN-ISSUES-v0.12.0.md) list them, and the
  [enterprise checklist](../enterprise.md#7-hardening-against-bought-repair-evidence-419)
  says how to block the rest.

D-199 measured its cost on main `7cd8549c`: 18 of the fixed corpus's 3,600
commits move from pass to block (7 Python, 11 JS/TS), and 53 of D-088's
1,263 skip, xfail and conftest commits, none adjudicated. The fixed-corpus
comparison below measures the release as a whole.

## Three holes beside it (D-201)

Before 0.12.0 Nelson chose to close three holes that the 0.12 design found
beside #419's residual. They are closed in part.

- **`unittest.mock.ANY` is a tautology.** An equality with it as a whole
  operand passes whatever the subject is. The Python frontend reads it, and
  the other spellings that hold for every value, as the `TAUTOLOGY`,
  `TYPE_SHAPE` or `TRUTHY` strength, so rewriting an expected value into
  one is `ASSERT_WEAKENED`, beside a version bump or not. `ANY` is read
  through the file's imports, and a bare name as Python reads it.
- **A single test's skip must provably run somewhere.** The compatibility
  credit (D6) goes to a single test's skip only when its condition is
  provably false in some environment of the matrix (CPython 3.11 to 3.14
  and PyPy 3.11, each platform's two machines), and the gates a change adds
  must leave such an environment together with the gates the test had. A
  condition that is always true once a part checkwash cannot read is mixed
  in no longer earns it. A suite-level collection control keeps the old
  reading.
- **`assertCountEqual` drops order.** `assertEqual` (and the other ordered
  equalities, or a bare `assert ==`) rewritten as `assertCountEqual` on the
  same subject is `SUBJECT_NORMALIZED`.

D-201 measured its cost on main `54113c06`: on D-088 2 of 1,263 commits
move from pass to block, on the fixed corpus 1 of 3,600, and outside both
samples 6 of the 1,273 commits in D-088's repositories that touch a skip,
all from pytest's 2007–2013 history (that set informed D-201's later review
rounds, so it is no longer out of sample either). Neither sample holds an `== ANY` or an
`assertCountEqual` rewrite, so those rules' cost is unmeasured. What still
passes is in the [known issues](../KNOWN-ISSUES-v0.12.0.md).

## The release tag at the Action commit (D-200)

From v0.12.0 the release tag points at the release's Action commit A, the
commit the README recommends as the Action pin after publication, instead
of at the release merge M, and its message names M on one line,
`Release-Merge: <M>`. The PyPI package and the pyz are still built from M,
whose second parent's parent is A and whose `doctor` differs from A's only
in its own Action pin line, set to A. So pin updaters such as Dependabot
and Renovate, zizmor and `git ls-remote` see the recommended pin as the
tag's commit (inferred from those tools' documentation, not run).

- **Install the CLI from PyPI or the pyz.** A CLI installed through Git
  from the tag is A's, and its `doctor` rejects the release's own Action
  pin ("workflow analysis incomplete", exit 1). The README installs only
  from PyPI and the pyz.
- **The Release page's source archives** are A's tree, which differs from
  the sdist's source in `doctor`'s own Action pin line.
- **v0.11.0 stays as published**: its tag stays on its merge commit and its
  recommended pin on `v0.11.0^2^1`.
- **The new path first runs for real here.** The tag, release-event and
  public-visitor stages under the new rule have run only on owned synthetic
  chains. A tag cannot be moved, so a failure found after the push may cost
  a v0.12.1.

## Evidence and scope

Each release stage (pull request, main, tag, release event and public
visitor) is collected afresh on LAPTOP-01AGNPJU, Windows, CPython 3.11.9,
`HUMAN_AUTHORIZED_LOCAL_PJU_NOT_EC_POOL`, one route for the whole chain, as

public files are verified. **1.0 readiness remains NOT_MET**: these in-sample
comparisons establish no held-out rate, adoption cohort or unexecuted
platform coverage, and Nelson's stop before 1.0 remains in force.
