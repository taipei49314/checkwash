# v0.5.0 release guide

The maintainer authorized this release on 2026-10-01 after the red-team
reports [#172](https://github.com/taipei49314/checkwash/issues/172)–[#182](https://github.com/taipei49314/checkwash/issues/182)
were worked through PRs #183–#192. The one-time scope is recorded in
[RELEASING](../RELEASING.md). The
[GitHub Release](https://github.com/taipei49314/checkwash/releases/tag/v0.5.0)
is the publication record. Preparation alone does not mean the version is
published.

## What changes

Each report below now reaches an existing detector. The THREATMODEL row
named in brackets holds the exact boundary, pins and residuals.

- **A skip in the setup a test runs** (#172, row 104). An unconditional
  `pytest.skip()` or `pytest.xfail()` (or a raised skip exception) in a
  conftest fixture, a same-file fixture the test reaches, or xunit setup
  reports `TEST_DISABLED`. A conftest fixture reports even when nothing
  requests it yet.
- **A selector over edited tests** (#173, row 105, closed in part). A first
  pytest config that deselects the suite, for example `-m "not slow"` over a
  marked test, blocks even when every collected test sits in a file the same
  diff edits or renames. This proof runs only where the resolved collection
  inventory runs. It is withheld when CI passes explicit pytest targets or
  collection options (including `PYTEST_ADDOPTS` or `-o`), when a conftest
  carries collection controls or `pytest_plugins`, or when a setting is
  ambiguous; there the first-adoption warning stays.
- **A package manifest's test command** (#174, row 106). When a diff changes
  what `package.json` or a Pipfile `[scripts]` runs as its tests
  (`scripts.test`, `test:*`, scripts that invoke a recognised runner, and
  scripts that `test`/`test:*` name one hop away), the manifest is CI for that
  diff. It no longer buys the opaque-change exemption, and `|| true` or a
  narrowing option inside the command is a CI weakening.
- **Jest's zero-configuration layout** (#175, row 107). JS/TS files under
  `__tests__/` and bare `spec.*`, `test.jsx` and `test.tsx` names are tests,
  except paths already resolved as snapshot, guardrail, CI or lockfile.
- **JS/TS unit liveness** (#176, #178, row 108). Block-level skips
  (`describe.skip`, `xdescribe`), options-object skips (`{ skip }`, `{ todo }`),
  sibling focus (`.only`, `fit`), inverted oracles (`.fails`), Vitest
  `skipIf`/`runIf`, and imperative `t.skip()`/`this.skip()` report
  `TEST_DISABLED`. Conditional JS disables get no compatibility-gate credit.
- **JS/TS module mocks** (#177, row 109). A newly installed first-party
  stand-in (`vi.mock`, `jest.mock`, their ordered forms, node:test
  `mock.module`, or a replacing spy) that an existing unit's own assertion
  reads reports `TEST_PATCHES_SUBJECT`.
- **Hand-rolled JS tolerances** (#179, row 110). `Math.abs(a - b) < eps`
  inside a truthy oracle or an ordering matcher is an absolute tolerance, so
  widening `eps` reports `TOLERANCE_LOOSENED`.
- **chai assertions** (#180, row 111, closed in part). chai `expect` chains with
  a single terminal and the chai `assert` interface map onto the existing
  strength lattice. A `closeTo` delta is recorded as the same absolute bound
  as a hand-rolled tolerance.
- **CI control flow** (#181, row 112, closed in part). A statically false
  step or job `if:`, a `needs:` on a disabled job, a trigger set no pull
  request can reach, or a pre-commit test hook moved to the `manual` stage or
  removed is a CI weakening, even when every runner line is unchanged.
  Dropping `pull_request` while an unfiltered `push` remains still counts as
  reachable and stays a warning.

Report #182 confirmed two documented residuals (rows 91b and 100) and changes
nothing.

The two performance budget checks in `tests/gates/test_perf.py` are skipped on
macOS by maintainer decision; the Linux and Windows legs still enforce the
unchanged budgets.

## Upgrading

The finding and IR JSON shapes, the severity contract and the exit codes are
unchanged. Some existing findings now carry a different fingerprint, which is
why this is a minor release ([D-063](../../DECISIONS.md)). An allowlist entry recorded on v0.4.2 for one of
these shapes stops matching and has to be recorded again:

- `CI_WORKFLOW_TOUCHED` where a collection proof now resolves against the
  whole base suite (#173), where a promoted package manifest's own finding or
  another CI file's restatement changes (#174), or where a disabled runner adds
  a control-flow reason (#181);
- `TEST_DISABLED` on JS/TS units that v0.4.2 read as removed (`.fails`,
  `skipIf`/`runIf`, `.concurrent.skip`, focus) and now reads as disabled (#176,
  #178), and on deleted chai-only units, whose identity now includes their chai
  assertions (#180);
- `SCOPE_DRIFT` and `SNAPSHOT_CODE_COCHANGE` on files whose role changed: a
  package manifest promoted to CI (#174), and JS/TS paths that moved between
  production, test, snapshot, guardrail and CI roles (#175).

Some verdicts change too. Newly blocking on test-only diffs: the shapes above;
honest JS platform or capability gates and imperative skips; moving a gated or
skipped JS unit; and the CI edits #181 lists as accepted, such as `if: false`
on a flaky job or removing a pytest pre-commit hook. Newly passing: moving
`x.test.ts` to `__tests__/x.ts`, and some mixed Jest/chai swaps in Vitest
files. The PR bodies list the sets known at release; more were found after
publication (below).

This list comes from reading the changes. The fixed Python sweep below records
no fingerprints; in its window the blocked commits, blocking findings and
per-rule counts are unchanged.

**Found after publication (2026-10-02).** A re-check of v0.5.0 found more
edits that v0.4.2 blocked and v0.5.0 passes. Each issue lists the exact
cases, the nearby cases that still block, and the questions open for the
maintainer. The verdicts come from in-process engine runs on the source of
both tags; the CLI and the released files were not run.

- [#197](https://github.com/taipei49314/checkwash/issues/197): a JS/TS test
  file that resolves to another role is not parsed as a test, so no test rule
  reads it. The role comes from a shell shebang or a `Makefile` name prefix
  plus a test runner name (promoted to CI), a `.github/workflows/`,
  `.circleci/` or `.buildkite/` directory, an `expected/`, `golden/` or
  `__snapshots__/` directory, or a `roles` glob for `ci`, `snapshot`,
  `lockfile` or `conftest` in the checkwash config.
- [#198](https://github.com/taipei49314/checkwash/issues/198): in a Vitest file,
  some Jest matchers rewritten as a chai `expect` chain or a Vitest `assert`
  call that asserts something else, beyond the `toBeNull()` -> `.to.exist`
  named at release: `toBeLessThan(80)` -> `.to.be.above(80)`, `toBe(78.75)`
  -> `assert.equal(value, 75)` or `.to.be.undefined`, and
  `toBeCloseTo(v, 2)` -> `.to.be.closeTo(v, Infinity)`. Rewrites whose two
  sides both carry a literal, a negation or a finite delta still block.
- [#199](https://github.com/taipei49314/checkwash/issues/199): a conftest fixture
  whose setup always ends in skip or xfail, anywhere in the tree and whether
  or not a test requests it, withholds the resolved collection inventory. A
  first pytest config that narrows `python_files` or adds a filtering
  `addopts`, or a changed `python_files` value, then warns instead of
  blocking. Two runtime hooks in a conftest already withheld the inventory
  before v0.5.0, and still do: a `pytest_runtest_setup` that always skips
  (#199 row H1) and a `pytest_runtest_makereport` hookwrapper that rewrites
  the outcome (row R1). Both pass at warn on v0.4.2 and v0.5.0, so they are
  not regressions; THREATMODEL row 105 names only parse failure, collection
  controls and `pytest_plugins` as withhold reasons. The #199 fix stops every
  runtime control from withholding (ruling 199.Q1).
- [#196, 186.7](https://github.com/taipei49314/checkwash/issues/196#issuecomment-5945152490):
  moves between other recognized layouts read as benign too, for example
  `x.test.tsx` -> `spec.tsx`, `test.tsx` or `__TESTS__/x.ts`, and
  `x.test.ts` -> `spec.ts`. On `main` after the release, the runner that a
  file's imports or the base manifest name judges the move (rows M0-M5 and
  P1-P3 block), and `__TESTS__` is collected by no runner.
- #196, 186.8: under a task contract, an out-of-scope production file named
  like a Jest test (`spec.ts`, `Test.tsx`, `test.jsx`) is a test, so
  `SCOPE_DRIFT` on it is reported at warn instead of high.
- #196, 187.4: focus (`.only`, `fit`) that leaves no unit in the file
  unfocused reports nothing. v0.4.2 blocked unit-level focus only because it
  read the focused unit as removed; `describe.only` over every unit passed
  there too. Mocha and Jasmine apply focus to the whole suite (from their
  documentation as recalled; not checked against it or run). On `main` after
  the release, such focus is reported for the file unless a `vitest` or
  `@jest/globals` import, or a base manifest naming only Jest or Vitest,
  proves the runner keeps focus in the file (rows F3-F6 block).

## Evidence and limits

- **Pull-request CI.** On each of PRs #183–#192 the nine OS/Python test legs
  failed only the pre-tag parity test, apart from one performance-budget miss
  on each of #184 and #189 that passed when the job was rerun. `qualify` stayed
  red on the disclosed legacy v0.3.3 byte comparison, and the pinned-Action job,
  then on v0.4.1, stayed red at 13/283. Dogfood, install-from-tag,
  byte-compare and the source/wheel/pyz candidate contracts passed.
- **Fixed 1,800-commit Python sweep** of `3cef2a5` on the pool (estate T-494,
  run 36888070539): 48 blocks. Blocked commits, blocking findings and per-rule
  counts equal the published
  [v0.4.2 result](https://github.com/taipei49314/checkwash/releases/tag/v0.4.2)
  for all six repositories. Against the older reference arm (46 blocks) the
  sweep reports the two extra blocks v0.4.2 already had (click `1e4a5070`,
  rich `63d32001`). It is an already used regression window, not a held-out
  measurement.
- **Pool test run.** The same commit's pytest run on a Windows pool host
  passed 9,038 tests and skipped one; the one failure was the tag-parity gate.
  The run stops at its first failing gate, so the tamper verifier,
  `checkwash bench --local`, the zipapp build and `tools/qualify_zipapp.py` did
  not run on the pool for this commit.
- **No JS/TS history replay.** Most fixes in this release are JS/TS, but no
  independently selected JS/TS history replay was run for v0.5.0, so the
  false-positive cost of the new JS/TS blocks is unmeasured.
- **Partial closures.** #173, #180 and #181 stay open for the spellings their
  rows list as residual.
- **Recommended Action.** Under the one-release trust lag the recommended
  Action advances to **v0.4.2**, commit `23ef5929896187e4aac5889735c792e65af3e721`.
  It has the JS/TS callback and scalar-evidence foundation but none of the
  fixes above. Its engine is measured separately against the current
  assertion contract, which does not cover these fixes; any failing case
  stays visibly failed.
- **Frozen comparisons.** The legacy v0.3.3 quality byte comparison keeps its
  disclosed cross-version mismatch.

The release record links the final-source checks on the tag: the full suite on
nine OS/Python legs, self-check, install-from-tag, corpus byte comparison and the
source/wheel/pyz assertion contracts. Human product acceptance remains separate
from mechanical qualification.

## Try it on a change you understand

With Python 3.11+ and Git, after publication:

```sh
pipx install checkwash==0.5.0
checkwash --version
checkwash demo
checkwash check HEAD~1..HEAD --format json --coverage-report coverage.json
```

Exit 0 means no blocking finding, exit 1 means a blocked change, and exit 2 means
an analysis/input error. GitHub provides the offline `checkwash.pyz`; the wheel
and sdist are also published through the existing PyPI workflow.

Checkwash remains alpha. A pass does not prove correctness or honesty. This
one-time publication authorizes the downstream re-pins named in
[RELEASING](../RELEASING.md) and no other release.
