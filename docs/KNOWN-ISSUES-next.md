# Known issues on main after v0.8.0

This page collects the known limits of changes merged into `main` after
v0.8.0. Nothing on it is released. When the next release is prepared, its
known-issues page takes these rows over, with what that release measured.
A row marked *Existing* is a limit v0.8.0 already had that was documented
only after its release; the row says where it was found.

Residuals below were found by reading the code and the pull requests'
reviews, unless a row names another source. Unless a row says otherwise,
the acceptance sweeps of these changes have not run:
`NOT_RUN：工作機規則（POLICY work-machine-local），each sweep runs where the owner approves it`.
Their false-positive cost is unmeasured.

| [#212](https://github.com/taipei49314/checkwash/issues/212) JS/TS false-positive rate | There is no held-out or adjudicated JS/TS false-positive rate. The fixed 1,800-commit JS/TS set is in-sample, and each release compares only which of its commits change outcome between the previous release and the candidate ([release procedure](RELEASING.md)). The 39 commits that v0.7.0 and v0.8.0 both block there are not adjudicated, so how many of them are false blocks is unknown. [Results](../benchmarks/javascript-replay/results.md). |
| [#429](https://github.com/taipei49314/checkwash/issues/429) JS/TS tautologies | An assertion on literals alone, and an equality or inclusive bound with one operand on both sides, read as TAUTOLOGY. Truthy spellings of a self-comparison (`assert.ok(x === x)`), a subject of literals and builtins (`expect(String(1)).toBe("1")`), a name bound to a literal, `undefined`, `NaN` and `Infinity` as subjects, and self-comparison in `toBeCloseTo`, `toContain` or `within` still read at their old rung. JS/TS also has no reading of SPEC §5's `trivial` rule, so such a subject of literals and builtins still counts as a strong assertion wherever compensation is counted (D4, D5 and the split-or-rename budget): by reading, one such line written beside a deleted assertion can hold its finding at warn. SPEC §3 names this residual; no fix is scheduled. A tautology in a catch adds no always-pass proof to #431's. [Details](js-reachability.md). |
| [#429](https://github.com/taipei49314/checkwash/issues/429) JS/TS reachability | An assertion after an unconditional `return` or `throw`, under a branch a literal-only folder decides dead, or behind `false &&`, is not the test's. A `return` in a loop, `do`, `try` or labeled body ends nothing after it; `break`, `continue`, `switch`, `for (... of [])` and `const` bindings are not read; and wherever the walk cannot prove a statement's end (a line break next to a template or regular expression, a typed function declaration, unpaired brackets), the assertions after it keep their reading. A test registered in dead code is outside this change. The walk refuses every text the shared token stream was found to misread, but one it misreads and no refusal notices can still make live code read as dead, which reports `ASSERT_REMOVED` ([#490](https://github.com/taipei49314/checkwash/issues/490)). [Details](js-reachability.md). |
| [#431](https://github.com/taipei49314/checkwash/issues/431) always-passing catch assertions | Unchanged since v0.8.0, listed here because their fix moved from #429 to [#513](https://github.com/taipei49314/checkwash/issues/513). A catch that swallows the guarded assertion still passes beside number and string literal equality (`expect(1).toBe(1)`), `toEqual(true)`, `toStrictEqual(true)`, loose `assert.equal(true, true)`, `expect(undefined).toBeUndefined()`, non-boolean literal truthiness, a literal message argument, or a binding compared with itself, so changing one token of `expect(true).toBe(true)` turns its block back into a pass. #429 added no shared always-pass helper for them; #513 is their fix. TypeScript wrappers, chai BDD, AVA `t.true(true)`, tap `t.ok(true)`, a local bound to a literal, assertions on the caught binding that cannot fail, unrelated always-true state and equal-count exchange stay named residuals. The Python counterpart (`except Exception: assert True`) is [#496](https://github.com/taipei49314/checkwash/issues/496). [Details](js-catch-swallowing.md). |
| [#488](https://github.com/taipei49314/checkwash/issues/488) helper-method skips | A known false block, which the next release is the first to carry: v0.8.0 does not contain #306's change. A test that calls, through `self`, a helper method holding a guarded skip whose guard is not a compat gate (SPEC §5 D6) now reads as not live (D2), as it already did with that skip in its body, its setup or a helper function. So when a change merges or moves tests into ones that call such a helper, the old tests can lose their move or restructure credit, and their `TEST_DISABLED` findings then go to high unless repair evidence or another de-escalator holds them at warn, and at high they block even when the change only adds coverage. #306's acceptance sweep, which ran in part (2026-10-17, human-authorized local PJU, NOT EC pool; D-145), found one such block in the commits it judged, scrapy `fada8be1db`; how often this happens is not known. The block stays until a later change removes it. Meanwhile you can exempt these findings by fingerprint only through an `allow.toml` entry already on the base side; one added in the blocked change itself shows as `EXEMPTION_ADDED` and does not lift the block. Further cases are recorded on #488. |
| [#421](https://github.com/taipei49314/checkwash/issues/421) assertion-level exemptions | Since #477, an exemption for nine assertion-level rules covers only the reviewed change (D-146). EXPECTED_VALUE_HARDCODED, CONFTEST_PATCHES_PROD and TEST_PATCHES_SUBJECT keep before-only keys: their exemption is not bound to the reviewed change, so until it expires it also covers another change that yields the same key. They are named residuals (THREATMODEL row 136). TEST_DISABLED moved in [#512](https://github.com/taipei49314/checkwash/issues/512) (next row). The keys' normal form does not know JS/TS regular-expression literals: a backtick in one opens a template and a quote opens a string, so the whitespace after it is kept, and reformatting such a line changes its key and needs a new approval. That fails closed. The term report's footer counts exempted findings without listing them ([#514](https://github.com/taipei49314/checkwash/issues/514), deferred until after 1.0). This change's acceptance sweep did run, on 2026-10-17 over the standard set and D-088's sets: no outcome or verdict changed, only keys. The replayed repositories hold no exemptions, so it measured neither the new blocks nor the re-review of existing exemptions (D-146). |
| [#512](https://github.com/taipei49314/checkwash/issues/512) TEST_DISABLED exemptions | Since #512, a TEST_DISABLED exemption covers only the reviewed change (D-169). Its key binds what the change did: an added marker's text and its guard, the guard before and after with what every marker of that name runs under, which parametrize or table rows were deleted or newly disabled with the live counts, a removed test's complete assertions, or how a focus added to a file is spelled. When a test holds several markers of one name, each one added binds its own text and guard; when the added ones cannot be told from the others (for example, another of that name was edited in the same change, one was moved in from a helper, or one was paired with a marker spelled another way), each binds every marker of the test before and after. A finding's evidence is still the last marker of its name in the test, so with several of one name it can show another marker than the one its key binds: before you record a key, read the added marker in the change itself, not only the evidence. Legacy TEST_DISABLED keys are retired, so re-run each reviewed change and record its new key. The key binds what checkwash reads, so in five shapes another change still gets the same key: a JS/TS imperative skip (`ctx.skip()`, `t.skip()`, Mocha's `this.skip()`) records no guard, so a guarded one and an unguarded one get the same key; the rows of a table checkwash cannot read (a parametrize list that is not a literal, a JS/TS table whose rows are not counted) are bound only by their counts; a path added to an unguarded `collect_ignore` binds no path; a guard made always true by editing a constant it names binds the guard's text, not the constant's value; and a focus added to a file binds its spelling (`describe.only`, `fdescribe`, an `only` option), not the block it is on. Findings of TEST_DISABLED in one unit now sort by key, so their order in a report can change. |

By reading, undici's runner fails no run on a changed result today, so the edit hides the regression in the record, and `skip` stops the file from running. Review the diff of such a file by hand. No detector is scheduled (D-160). Source: the v0.8.0 acceptance sweep (D-140), whose JavaScript batch left this file unread in 10 undici commits. [Details](assertion-coverage.md#expected-failure-records-a-test-runner-reads). |

| [#424](https://github.com/taipei49314/checkwash/issues/424) function-level `__test__` | Since #424 a later rebinding of a test's name is read, but a function-level `test_x.__test__ = False` appended after the test is not. pytest no longer collects that test, and checkwash reports nothing: exit 0, verdict pass, no findings. So a change that only appends that line under a failing test takes it out of the run and passes, while `__test__ = False` at module scope blocks as `TEST_DISABLED`. This was reproduced on `main` on all nine hosted `test` legs of run [39215282880](https://github.com/taipei49314/checkwash/actions/runs/39215282880) with pytest 9.1.1 (draft PR #518, not merged); there the file held only that test, so pytest collected nothing and exited 5. The result is recorded on [#424](https://github.com/taipei49314/checkwash/issues/424#issuecomment-6263373438) and [#280](https://github.com/taipei49314/checkwash/issues/280#issuecomment-6263373911). The class-method spellings (the same line in a class body, or `TestX.test_x.__test__ = False`) were not run. A fix shares #280's attribute reading, which [#504](https://github.com/taipei49314/checkwash/issues/504) defers until after 1.0; no separate issue is filed until a fix is scheduled. The change #424 made was measured by the 2026-10-17 acceptance sweep of #421; the review of the commits it changed is on [#424](https://github.com/taipei49314/checkwash/issues/424#issuecomment-6240866014). |
| [#500](https://github.com/taipei49314/checkwash/issues/500) `--task` at the root | A base miss at the root is an engine error when the base tree holds, compared with case ignored, a file, symlink or submodule at a prefix of the task path, or the path itself in another case. The comparison is on text, so on a case-sensitive checkout an untracked `task.md` beside a committed `TASK.md` is refused too. A task file the base does not hold at all is still read from the working tree, now with one stderr line: a CI step that names a task file the base never had still lets each change supply its own contract; so does a task path that names a base submodule exactly, when the head puts a file there. Inferred: other spellings a file system treats as the same file are not compared, such as Unicode normalization (NFC against NFD on macOS), names a file system's own case table joins but Unicode case folding keeps apart (`ı` against `I`, if NTFS's table maps them) and, on Windows, trailing dots or spaces, 8.3 short names and alternate data streams. `doctor`'s root lookup now gives up after 5 seconds per query (about 10 seconds from a subdirectory); when its first query times out, `doctor` reports on `--repo` as given with no message. |
| [#454](https://github.com/taipei49314/checkwash/issues/454) unread sides in the output | A changed side over the 1,000,000-byte limit that checkwash set aside unread is now listed under the optional `unread` key of `--format json`, as a SARIF notification and as a `!` line of the term report. A validator that rejects unknown keys meets `unread` only on a run that has one. Not listed: the readable side of a range-mode rename whose other side is over the limit, though that whole change was set aside; the skip of a root `poetry.lock` or `uv.lock` over the limit at the base, which stays a stderr note (when the diff also changes that lockfile, the change's sides over the limit are listed like any other); and the side a size refusal names, since that run gives no findings report (option (d) of [#456](https://github.com/taipei49314/checkwash/issues/456), now part of #454, which stays open for it). The Stop hook's JSON and `--emit-ir` name no unread side. A worktree side's size is its size on disk, so a text file near the limit can be listed on a CRLF checkout and read on an LF one. [Details](stability.md#machine-findings-contract-findings_version--ir_version). |
| [#463](https://github.com/taipei49314/checkwash/issues/463) rewritten stored expectations | A snapshot, golden or expected file rewritten beside nothing but a new Python production module now blocks (`EXPECTED_VALUE_CHANGED` at high). A pytest file kept under `golden/`, `expected/` or `__snapshots__/` is such a file too, so adding a test there for a new module, an honest edit that used to pass, now blocks the same way. The owner accepted that cost (D-157); #463's sweep will count it. Beside a changed symbol in any existing or deleted Python production file, whether or not a test reaches it, or beside an edit to an existing production file checkwash cannot read, such as a template, it still holds at warn as `SNAPSHOT_CODE_COCHANGE`. When test logic changes anywhere in the diff, a new test in an unrelated file included, that warning goes too, and nothing is reported. checkwash does not know which test reads a stored file, so the check is diff-wide (THREATMODEL row 132). |
| [#428](https://github.com/taipei49314/checkwash/issues/428) JS/TS tables, what is still not read | A `test.each`, `it.each` or `test.for` table is one unit, and its rows are read when they can be counted: an inline array with no spread or hole, a tagged template, or a same-file `const` bound once to an array and read only as a table argument. Rows are not compared between two tables when either side cannot be counted (a conditional, an import, a `let`, a `const` changed or read anywhere else). Not read either: the rows of a `describe.each` table; a table with a computed title, or written with a TypeScript type argument (`test.each<Row>([...])`), which is no unit; a callback declared elsewhere; an expected value reached through a member (`row.expected`), an index or a local computed from a cell, or passed to a matcher such as `toContain` or `toMatch`; any column of a callback whose parameters hold a comma inside a type argument (`m: Map<string, number>`); a row deleted while another with the same answer is appended, when either holds a cell that is not a Python literal, such as `true`, `null` or a template. A table's assertion text that appears again elsewhere earns the move credit however its rows changed, and two tables with one title share one exemption key. No issue is open for reading `describe.each` rows or for a fold of plain tests into a table; one opens when a fix is scheduled. |
| [#428](https://github.com/taipei49314/checkwash/issues/428) JS/TS tables, new passes | JS tests pair by position, so a plain test deleted in a file that gains a `test.each`, `it.each` or `test.for` table whose rows can be counted pairs with that table and is no longer reported as removed. The change passes when the pair shows nothing else, as when the deleted test asserted nothing, or asserted `toBeTruthy()` on a call whose literal argument the table turns into a column. v0.8.0 reports the deleted test as removed. A plain test wrapped in such a table with its assertion unchanged also passes now, as intended. |
| [#428](https://github.com/taipei49314/checkwash/issues/428) JS/TS tables, new blocks | In a test-only change these now block, as their Python counterparts do: an expected cell corrected, an input cell changed under the same answer, a row deleted or deduplicated. JS tests pair by position, so turning a table into plain tests, `test.each` into `describe.each`, a table into a loop in one test, or moving a table out of the file beside a new test, reads as tests lost or rewritten. Folding plain tests into a table still blocks, as before. Renaming only the parameter an expectation reads (`sum` to `want`) reads as `EXPECTED_VALUE_CHANGED`, as renaming such a local does in a plain JS test. A plain test wrapped in an imported or computed table reads as lost. |
| [#434](https://github.com/taipei49314/checkwash/issues/434) Python assertions paired by subject | An old assertion now pairs first with a new one on the same subject, written out or through one plain local binding, so a precondition above a rewritten `==` no longer blocks; `match=` added to a bare `pytest.raises` is no finding. A new oracle that checks another subject against another expectation still blocks, as on [#457](https://github.com/taipei49314/checkwash/issues/457)'s real commit: take a reviewed exemption for such a rewrite. An expectation moved into a local in the same edit (`expected = 20.0`) still reads as `ASSERT_SUBSTITUTED`. A membership assert whose needle is not a literal (`f"{n}/{n} cases blocked" in out`) checks the needle, not `out`, so a count guard written above it still takes the old `"7/7 cases blocked" in out` and blocks, as on the dogfooded commit behind THREATMODEL row 85. A name bound any other way (a parameter, `global`, a tuple, a loop target, an annotation) or read in a nested function is taken as written. `approx(x)` -> `approx(x, abs=...)` still reads as new slack, and two approx checks in one test still pair in span order. [Details](assertion-coverage.md). |

| [#496](https://github.com/taipei49314/checkwash/issues/496) Python always-passing handler assertions | A broad handler in a Python test or conftest that does not re-raise and whose every assertion is proved to always pass now swallows the assertion its `try` guards, and is reported under its first line followed by `[always-passing assertion]`. | [#469](https://github.com/taipei49314/checkwash/issues/469) large Python test files | A test file over 30,000 syntax nodes no longer stops the run at the subject-replacement pass, which now shares the stand-in pass's 200,000-node limit; over that limit the run still exits 2, naming the file, its side and its node count. That growth is a residual: the run did not split the time before the pass into its steps (53.5 seconds for the helper-call shape at 200,000 nodes), so which step grows is unknown, and a measurement that splits it, for example of the stand-in pass, goes to the pool after the release. It also makes once per file, not once per test, the module and repository checks for a test whose callee changed to a local `math.gcd` helper and for a test that calls a module helper whose assertion compares with a parameter (`check(1, 2)`, with `def check(x, y): assert f(x) == y`); only in a test file of at most 4,096 syntax nodes are the file's other functions still checked once per `math.gcd` test. The stand-in step limits are unchanged: a trace over 20,000 steps, or an analysis over one million, still exits 2, now naming the counter, the file, the side and the test; which counter fires on the 17 step-limit commits that #469's ruling counts is not measured. Two stand-in limit refusals still name nothing: the strict inventory path limit and the source read limit. In the Claude Code Stop hook all of these stay non-blocking messages ([#506](https://github.com/taipei49314/checkwash/issues/506)).
