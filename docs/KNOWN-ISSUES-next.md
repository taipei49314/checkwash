# 0.11 candidate — 2026-10-28

The 0.11 candidate adds a Claude Code PreToolUse ask and changes how the
Stop hook blocks ([D-189](../DECISIONS.md)). It also stops counting a
proven Python failure relay as an added swallow
([D-190](../DECISIONS.md)), and closes #419 as a documented residual
rather than a fix ([D-191](../DECISIONS.md), the #419 row below). After an
outside report on #130, it proves a lone `pytest.raises` carrier like an
assertion, lets a test file that lost no oracle mass be a D5 candidate, and
stops reading parametrize cells that never reach the test as written
([D-192](../DECISIONS.md), the raise-carrier rows below). Nothing
here is released. One pre-registered Claude Code lifecycle receipt
exercised both hooks at head `f4253f7c`, in `-p` mode only, on Claude Code
2.1.260 with haiku on Windows; D-189 gives what it showed, and the rows
below what it did not. Both hooks are author-side checks: the required CI
check in range mode remains the gate. The Stop hook applying
`oracle_freeze` by default is deferred. The rows below are named residuals,
found by reading the code and its design review unless a row names another
source.

| Scope | Known limit and what it means for you |
| --- | --- |
| PreToolUse ask: tools the matcher does not name | The handler's matcher names Edit, Write and MultiEdit only. An edit made through Bash (`sed`, `python -c`, `git checkout`, `git apply`, `git mv`), NotebookEdit or an MCP file tool never reaches it, and whether a subagent's tool calls reach it is not verified. Such edits are seen only by the Stop hook and the required CI check. |
| PreToolUse ask: Python test files only | Only a `.py` path judged a test is analysed: role `test` or `conftest` under the base policy, or collectable by pytest. JS/TS tests are not asked about in 0.11, because the replay measured Python test edits only. An edit to any other path is not analysed, though a finding that an edit to a judged test surfaces on another path counts. |
| PreToolUse ask: rules outside the five | It asks only on ASSERT_WEAKENED, ASSERT_REMOVED, TEST_DISABLED, TOLERANCE_LOOSENED and BROAD_EXCEPT_ADDED at high or above. The other oracle rules never ask, so rewriting an expected value to match the current output (EXPECTED_VALUE_CHANGED and its family) goes ahead silently, as do ASSERT_SUBSTITUTED, SUBJECT_NORMALIZED, SUBJECT_INPUT_CHANGED, EXPECTED_VALUE_HARDCODED, CONFTEST_PATCHES_PROD and TEST_PATCHES_SUBJECT. In the replay behind D-189, the blocks on expectation rules alone were 43, with two unexplained loosenings. A finding of the five held below high does not ask either. The threshold is fixed at high and does not follow `fail_on`, and the hook forces `oracle_freeze` where the Stop hook does not, so the two hooks can disagree on the same change, either way. |
| PreToolUse ask: runner configuration | Runner settings are not test files, so the hook never analyses them: `pytest.ini`, `addopts`, `-k` or `--deselect` in `pyproject.toml`, tox and nox files, CI workflows. A change there that narrows what runs is seen only by the Stop hook and CI. |
| PreToolUse ask: renames and new files | A new file has no before side, so a weakened copy of a test written as a new file has no units to weaken, and deleting or moving the original through Bash is not seen. A weakening split across files this way, or across edits that each look harmless, can pass the hook. The Stop hook and CI see the whole change. A new file is still asked about in three cases ([D-191](../DECISIONS.md)): a broad `except` in it that swallows an assertion, unless it is a proven failure relay; suite-level controls in a new `conftest.py`, such as `collect_ignore`; and a file over the 1,000,000-byte source limit. |
| PreToolUse ask: the agent-written baseline | Each edit is compared with the file as it is in the working tree now, which the agent wrote. An edit made through Bash, an edit the user approved at the ask, and an edit the hook could not predict all become the next edit's before side and are not asked about again. |
| PreToolUse ask: engine errors | Under the default `on_engine_error = "pass_with_warning"`, an edit to a judged test that cannot be analysed, or gets no answer within 30 seconds, goes ahead with only a `systemMessage`, and whether Claude Code shows that message to the user is not verified. By reading, Write alone can reach the node limits ([#506](https://github.com/taipei49314/checkwash/issues/506)), the 64-importer limit of the root assertion-helper search, and the directory-symlink refusals (THREATMODEL row 128). Under `"block"` the hook asks instead. |
| PreToolUse ask: prediction gaps | The hook predicts the bytes an edit leaves from the tool input and answers `{}` where it cannot: a file that is not UTF-8, a MultiEdit in a shape other than `edits` of `old_string` / `new_string` / `replace_all`, a lone surrogate in the input, an `old_string` that does not match exactly, as in a file with mixed line ends. If Claude Code's Edit matches differently, for example by normalising quotes (not verified), the hook judges other bytes than are written. A concurrent write between the hook and the edit is not seen. Inferred: on macOS's default case-insensitive file system, a path spelled in another case keeps that spelling, so its role can differ from the file actually written. Input the hook does not read gets `{}` too, even under `on_engine_error = "block"`: hook input over 8,000,000 bytes, or not complete within 10 seconds ([D-191](../DECISIONS.md), THREATMODEL row 169). A Write that large carries a file over the 1,000,000-byte source limit, which the Stop hook's size block (#456) blocks on every stop. An Edit or MultiEdit that large can leave a file under the limit, which the Stop hook judges at its own severities, without the forced `oracle_freeze`. |
| PreToolUse ask: Claude Code behaviour observed once, in `-p` only | The lifecycle receipt behind D-189 was one run, of Claude Code 2.1.260 with haiku on Windows in `-p` mode, where an ask becomes a denial, and it exercised one Edit with one rule, ASSERT_WEAKENED. Under acceptEdits and under bypassPermissions alike, that Edit was denied with the hook's reason and the file was left unchanged, so bypassPermissions did not skip the ask there. Default, plan and auto modes were not run. No interactive session was run, so the permission prompt you would see is not verified in any mode, bypassPermissions included. Claude Code's hooks documentation (read on 2026-10-28) does not say whether a hook's `ask` prompts in bypassPermissions mode or whether `systemMessage` on PreToolUse output reaches the user, and it does not document MultiEdit's input. Also not verified: a Write call, a MultiEdit call, the other four rules, the size ask and the engine-error ask, other Claude Code versions, models and platforms, the ask's precedence against another hook's `allow`, whether Claude Code rereads hook settings changed during a session, how a write through a link lands, and whether the hook's working directory follows the session's (the handler runs with `--repo` at its default, `.`). |
| PreToolUse ask: `-p` runs | In a `-p` run nobody can answer, so Claude Code denies the edit and Claude reads the reason, which asks it to report the finding rather than make the same change another way. Nothing stops a retry through Bash or in smaller edits; the Stop hook and CI are the backstop. At the replay's exploratory rate (not pre-registered; the released v0.10.0 pyz on single-file diffs, not this handler), about one Python test edit in ten would be denied in such automation. |
| PreToolUse ask: exemptions and fingerprints | The ask honours an `allow.toml` entry at the session base, or at HEAD without a session record, and not one only in the working tree. Approving an ask records nothing, so the Stop hook can still block on the same finding. |
| Hook settings: machine-local by default | `hook install --agent claude-code` now writes `.claude/settings.local.json`, which Git often ignores. After 30 seconds the edit goes ahead unanalysed, as in the engine-error row. |
| Stop hook: one block per distinct set | A stop that arrives with `stop_hook_active` true, on the same blocking set checkwash last blocked on in the session, is released with a note for the user. So a stop is not blocked twice in a row on the same set while Claude continues; a different set, or another hook's continuation, still blocks. A released stop carries no session-commits note. The reason no longer offers `checkwash allow`, but the term report still prints it. This lowers the pressure on the agent, not enforcement: the Stop hook was never the gate. In the `-p` lifecycle receipt behind D-189 the release ran and the note appeared in the hook event output and as Claude Code's own informational notice, "Stop says: checkwash: this stop was not blocked again, ..."; whether the interactive UI shows it to you is not verified. |
| Stop hook: `.stop` records | The last blocking set is recorded under `<git-dir>/checkwash/sessions/`, which the agent can write (THREATMODEL item 2). By reading, a record forged to hold the current set's digest releases a continuation stop, another hook's included, that would otherwise block, and a deleted record makes the next continuation block again. |
| Stop hook: a block reported as a hook error | In the `-p` lifecycle receipt behind D-189 (observed, not a pre-registered outcome), checkwash's first block exited 0 with `decision: block`, and right after it Claude Code 2.1.260 emitted the stream-json notification "Stop hook error occurred · ctrl+o to see" (`key: stop-hook-error`), while its debug log records the hook as a success. So in `-p` stream-json a checkwash block can read as a broken hook. How the interactive UI shows a block is not verified. |
| Finding message: strengths read as values | The ASSERT_WEAKENED message names lattice strengths, as in "assertion strength EXACT_VALUE(90) -> BOUND(40)": 90 is the strength of an exact-value check, not the value the test expected. In the lifecycle receipt behind D-189 (observed, not a pre-registered outcome), Claude reported the blocked finding to the user and restated the weakened assertion's "Before" as `== 90`. Since [D-191](../DECISIONS.md) the Stop block reason, and the PreToolUse ask where its 1,200-character reason has room, follow an ASSERT_WEAKENED finding with the assertion's source text before and after the change, and an ASSERT_REMOVED finding with its text before, as in `(before: assert total() == 105.3; after: assert total() > 0)`, each side on one line, cut to at most 120 source characters and then escaped. The finding message, the term, JSON and SARIF reports, and the Stop hook's session note and released-stop note still name strengths as NAME(rank), so an agent relaying those can still tell you a wrong expected value; the test itself shows the assertion. |

| Failure relays: a broken relay | An edit that breaks a relay the rule reads, for example by removing its await, is not reported: 0.10 counted the handler as swallowing on both sides, and 0.11 reports no addition that 0.10 would not (THREATMODEL row 171). The bound reads only the after side's relays: an edit elsewhere in the file that makes an unchanged relay unread, such as a string equal to the loop's attribute name or a class attribute, reports nothing, while a new swallow added beside an existing relay still reports, and so does one that a relay made proven in the same change would otherwise offset. Its price: an honest relay added beside a handler with the same first line that is not a proven relay is counted, as on 0.10. |

v0.8.0. Nothing on it is released. When the next release is prepared, its
known-issues page takes these rows over, with what that release measured.

Residuals below were found by reading the code and the pull requests'
reviews, unless a row names another source. Unless a row says otherwise,
the acceptance sweeps of these changes have not run:
`NOT_RUN：工作機規則（POLICY work-machine-local），each sweep runs where the owner approves it`.
Their false-positive cost is unmeasured.
