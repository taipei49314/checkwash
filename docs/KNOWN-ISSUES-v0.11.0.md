# Known issues for 0.11.0

Status, 2026-11-03: the 0.11.0 release candidate, prepared in the release
pull request; not a published release record. The publication record follows
once the public files are verified.

0.11.0 adds a Claude Code PreToolUse ask and changes how the Stop hook blocks
([D-189](../DECISIONS.md)), stops counting a proven Python failure relay as an
added swallow ([D-190](../DECISIONS.md)), closes #419 as a documented residual
rather than a fix ([D-191](../DECISIONS.md)), proves a lone `pytest.raises`
carrier like an assertion and stops reading parametrize cells that never reach
the test as written ([D-192](../DECISIONS.md)), pays a moved or folded Python
test only where the repository's own pytest configuration collects it
([D-193](../DECISIONS.md)), and lets `doctor` accept the release's own Action
commit, which the README recommends after publication ([D-194](../DECISIONS.md),
[D-196](../DECISIONS.md)). The [release guide](releases/v0.11.0-public-launch.md)
describes each change and what this release measured. Both hooks are
author-side checks: the required CI check in range mode remains the gate. The
Stop hook applying `oracle_freeze` by default is deferred.

This page carries the rows of the 0.11 section of
[KNOWN-ISSUES-next](KNOWN-ISSUES-next.md) into the release's own page; that
section stays there as the dated preparation record. The rows below are
named residuals, found by reading the code and its design review unless a row
names another source. Earlier limits remain in
[KNOWN-ISSUES-v0.10.0](KNOWN-ISSUES-v0.10.0.md) and the pages it links. A
pass means that no known tampering pattern was detected; it is not a
correctness guarantee.

## Measured for this release, and what was not

- **Fixed-corpus comparison.** On all 3,600 fixed in-sample commits the
  published v0.10.0 and the 0.11.0 candidate gave identical results: Python
  1,734 pass and 66 block, JS/TS 1,759 pass, 39 block and 2 engine errors,
  with each ([release guide](releases/v0.11.0-public-launch.md)). On these
  commits the 0.11 changes alter no verdict and no report, so the comparison
  measures none of the costs the rows below name. In-sample counts, not a
  false-positive rate.
- **uvloop relays.** The three uvloop regression-test additions that 0.10.0
  blocks, which D-187 accepted as known costs for 0.10 only, pass on 0.11.0
  with no finding ([D-190](../DECISIONS.md)).
- **D-176's remaining risk, not measured.** An honest broad `except` added
  around an assertion in a Python test or conftest, beside an opaque
  production change, still blocks at high unless D-190 proves it a failure
  relay; how often history holds one is not measured. Claude accepts that
  risk for 0.11.0 only, as a delegated decision
  ([0.11.0 disposition](d176-cost-disposition-0.11.0.md)).

## Limits of the 0.11 changes

| Scope | Known limit and what it means for you |
| --- | --- |
| PreToolUse ask: tools the matcher does not name | The handler's matcher names Edit, Write and MultiEdit only. An edit made through Bash (`sed`, `python -c`, `git checkout`, `git apply`, `git mv`), NotebookEdit or an MCP file tool never reaches it, and whether a subagent's tool calls reach it is not verified. Such edits are seen only by the Stop hook and the required CI check. |
| PreToolUse ask: Python test files only | Only a `.py` path judged a test is analysed: role `test` or `conftest` under the base policy, or collectable by pytest. JS/TS tests are not asked about in 0.11, because the replay measured Python test edits only. An edit to any other path is not analysed, though a finding that an edit to a judged test surfaces on another path counts. |
| PreToolUse ask: rules outside the five | It asks only on ASSERT_WEAKENED, ASSERT_REMOVED, TEST_DISABLED, TOLERANCE_LOOSENED and BROAD_EXCEPT_ADDED at high or above. The other oracle rules never ask, so rewriting an expected value to match the current output (EXPECTED_VALUE_CHANGED and its family) goes ahead silently, as do ASSERT_SUBSTITUTED, SUBJECT_NORMALIZED, SUBJECT_INPUT_CHANGED, EXPECTED_VALUE_HARDCODED, CONFTEST_PATCHES_PROD and TEST_PATCHES_SUBJECT. In the replay behind D-189, the blocks on expectation rules alone were 43, with two unexplained loosenings. A finding of the five held below high does not ask either. The threshold is fixed at high and does not follow `fail_on`, and the hook forces `oracle_freeze` where the Stop hook does not, so the two hooks can disagree on the same change, either way. |
| PreToolUse ask: runner configuration | Runner settings are not test files, so the hook never analyses them: `pytest.ini`, `addopts`, `-k` or `--deselect` in `pyproject.toml`, tox and nox files, CI workflows. A change there that narrows what runs is seen only by the Stop hook and CI. |
| PreToolUse ask: renames and new files | A new file has no before side, so a weakened copy of a test written as a new file has no units to weaken, and deleting or moving the original through Bash is not seen. A weakening split across files this way, or across edits that each look harmless, can pass the hook. The Stop hook and CI see the whole change. A new file is still asked about in three cases ([D-191](../DECISIONS.md)): a broad `except` in it that swallows an assertion, unless it is a proven failure relay; suite-level controls in a new `conftest.py`, such as `collect_ignore`; and a file over the 1,000,000-byte source limit. |
| PreToolUse ask: the agent-written baseline | Each edit is compared with the file as it is in the working tree now, which the agent wrote. An edit made through Bash, an edit the user approved at the ask, and an edit the hook could not predict all become the next edit's before side and are not asked about again. |

| `doctor` and the release's own Action pin | *Fixed by [D-194](../DECISIONS.md) from 0.11.0.* A release cannot name its own commit, so since the README stopped lagging a release behind (2026-10-14), each published `doctor` has rejected the Action pin the README recommends once that release is verified: 0.10.0's accepts only v0.9.0's `d6eda4f6` and reports the v0.10.0 pin as "workflow analysis incomplete", exit 1. From 0.11.0 the release pull request's last commit changes one line, `doctor`'s own Action pin, to the commit before it, and that commit, `vX.Y.Z^2^1`, is the Action pin the README recommends after publication. A release's `doctor` accepts it and the pin recommended before the release, two exact SHAs built into the CLI, with no network read. **What remains:** `doctor` N rejects release N+1's pin, so upgrade the CLI and its local hooks before the Action pin; `doctor` 0.10.0 rejects the 0.11.0 pin (exit 1). No release stage replays the Action at the recommended commit: each replays it at the release's head, the pull request's last commit and then the merge commit with that commit's tree; the recommended commit differs from them only in that `doctor` line, and `checkwash check`, all the Action runs, never imports `doctor` (pinned by a test). |
