### The release's own Action pin (scheme S, D-194)

A release cannot embed its own commit SHA. From v0.11.0 a release's `doctor`
accepts two exact Action commits, both in its own source:
`_PREVIOUS_ACTION_PIN`, the Action pin the README recommended when the release
was prepared, and `_OWN_ACTION_PIN`, the release's own Action commit A. Each is
one line at column 0, `_NAME = "<40 lowercase hex>"`, with no trailing
comment; the release tools read that shape. After publication the README
recommends A. For v0.11.0 that is `v0.11.0^2^1`, not the commit the tag
points to ([D-194](../DECISIONS-archive-4.md)); from v0.12.0 the tag points
at A ([D-200](../DECISIONS-archive-5.md), below).

- **A, the content commit.** The version bump, release notes and every other
  change of the release PR, with both pin lines equal to the README's Action
  pin (step 1); `write` refuses, and the release bridge rejects, an A whose
  two lines differ. A may be a merge commit, such as an **Update branch**
  merge made before R.
- **R, the last commit.** On a clean checkout of A, run
  `python tools/own_action_pin.py write`. It sets only `_OWN_ACTION_PIN` to A,
  stages it, checks that exactly `src/checkwash/doctor.py` is staged and
  prints the `git commit` command; commit with it, hooks included. It refuses,
  exit 2 with nothing changed, a checkout with any change or untracked file, a
  `doctor.py` that the release bridge's pin reader refuses (below), a HEAD at
  the advertised version, a HEAD that is already an R, a HEAD whose own pin
  differs from its previous pin, and a worktree `doctor.py` whose bytes
  differ from HEAD's blob, line endings included. If `git add` or the
  staged-content check fails after the rewrite, for example on a stale
  `.git/index.lock`, it restores `doctor.py` and its index entry, then exits 2.
- **Nothing follows R.** No commit, no GitHub **Update branch** and no
  receipt, lifecycle or fixed-corpus record commit: those records go in the
  step-8 follow-up, or, for the fixed-corpus records, in A before R is
  written (D-196). A commit after R voids R and every PR-stage receipt
  collected on it, and `write` refuses that head, which keeps R's own line.
  To change the release PR after R, drop R: reset the PR branch to R's
  parent (`git reset --hard R^1` and a force push), make the change as one
  or more content commits (merging main, for an update), write R again on
  the last of them and collect again.
- **Main is frozen** from A until the release merge. Merge the README
  restructure, fixes and every other PR before A.
- **Merge commit only**, with the PR up to date with main: M's first parent is
  the base, its second is R, and its tree is R's. A squash or a rebase leaves
  A off main, and the `main` stage refuses it.
- **After an accidental squash or rebase merge**, which leaves R's own line
  on main's tip S, open a follow-up PR from S whose first commit sets
  `doctor`'s own line back to the previous pin and whose last commit is R,
  written by `write` on it; collect it through the release bridge's `pr`
  stage, merge it with a merge commit, and run the fixed-corpus comparison
  again, since R's own line changed. The reset commit is then the release's
  Action commit.
- **A fix after the release merge**, before the tag, follows the same
  pattern on main's tip: a PR whose first commit sets the own line back to
  the previous pin, then the fix, and whose last commit is R, written on the
  last content commit, which becomes the release's Action commit. Collect it
  through the release bridge's `pr` stage, merge it with a merge commit and
  run the fixed-corpus comparison again. An ordinary PR cannot carry the
  fix: its version differs from the advertised one.
- **To abandon the release**, a PR reverts the version to the advertised
  release's and `doctor`'s own line to the previous pin; the ordinary
  receipt bridge accepts that head.
- **Required checks only through the release bridge.** The release PR's four
  required checks and `PJU release evidence (pr)` come from the release
  bridge's `pr` stage. The ordinary receipt bridge refuses a head whose
  `[project]` version differs from `release/advertised.toml`'s, and a head
  whose `doctor` own pin differs from its previous pin.
- **What is not enforced.** That main stays frozen from A and that the
  step-8 follow-up is the next merge are documented procedure. Between A and
  the release merge nothing stops another PR, whose version equals the
  advertised one, from merging; the release PR must then take main, which
  voids R. After the release merge, the ruleset's strict up-to-date policy
  makes a stale PR take main first, and the ordinary receipt bridge then
  refuses it. That refusal holds only for receipts verified at a trusted ref
  that contains D-194, so from the D-194 merge on, ordinary receipts are
  dispatched only from main, and the pre-D-194 `review/collector-*-010`
  refs are not used for receipts.
- **R29 and the targeted uvloop diagnostic.** Since D-196 the candidate
  rule (below) accepts a `src/` tree that differs from the tag's only in the
  version string and in `doctor`'s `_OWN_ACTION_PIN` line, which `check`
  never reads (`test_check_never_imports_doctor`). So from v0.11.0 the
  fixed-corpus comparison and the targeted uvloop diagnostic may run on A,
  or on an earlier freeze that differs from the tag's `src/` only in those
  two lines, and their records (the run identities, the list, the owner's
  review, the release guide's R29 and JS/TS paragraph and the JS/TS results
  record) can go in the release PR's content before R is written. Records
  written after R go in the step-8 follow-up. The owner still reviews the
  list before the tag, and any other `src/` change after the comparison
  runs it again.
- **The Action replay.** Every release stage replays the Action at its head,
  R at `pr` and then M, which has R's tree; none replays it at A. That the
  Action at A is the release's rests on the one-line diff and
  `test_check_never_imports_doctor` (D-194).
- **Local checks**, advisory and not evidence: before collecting,
  `python tools/own_action_pin.py check --stage pr --head <R> --base <base>`;
  before tagging, up to v0.11.x `check --stage tag --head <M> --base <base>`,
  and from v0.12.0 `tag --head <M> --base <base>`, which runs the same rule
  and prints the tag command, then, after the local tag is made and before
  it is pushed, `check --stage tag` with `--main-report` and `--trusted`,
  which it requires from v0.12.0 (step 5). The tag
  stage applies the rule unconditionally, while at `main` it is skipped, and
  `check` only warns, when M's version equals its advertised version and its
  base's. The announced pin defaults to `ACTION_SHA` in
  `tools/pju_receipt_bridge.py`. Before each dispatch, also dry-run the
  verifier against the real receipt, as for v0.10.0.
- **From step 8 on.** Once step 8 moved the Action pin to v0.11.0's A, the
  pin differed from the advertised commit, that release's tag commit M, and
  from the verdict-baseline commit, also a tag commit: the previous
  release's until step 9 rotated it. This held for every later release-stage
  collection, from the step-9 rotation pull request's `pr` receipt (#586 for
  0.11.0) to the next release's stages, 0.12.0's included.
  `tools/collect_pju_release.py` falls back to the pinned Action checkout
  for `--advertised-source` and `--verdict-baseline-source`, so each such
  collection must pass separate checkouts at those commits; otherwise it
  stops on the checkout mismatch, after the full suite. The maintainer's
  local stage scripts were changed after 0.11.0's step 8: they pin the
  Action checkout at A and can add a checkout of the release commit for both
  sources. From v0.12.0 (D-200) the tag points at A, so after 0.12.0's step 8
  the Action pin and the advertised commit are the same commit, and after
  its step 9 the baseline commit is too: the fallback serves again. Every
  `tag`, `release-event` and `public-visitor` collection from v0.12.0 also
  passes `--tag-source`, a checkout of that release's own A, which the
  Action checkout is not until step 8; the local stage scripts
  (`prepare-stage.sh`, `run-stage.sh`) must add it.

What the release bridge checks (`validate_own_action_pin`, after the
previous-stage link and before the product evidence; the report records
`own_action_pin`):

- It applies at `pr` and `main` unless the head's `[project]` version equals
  both the `[release]` version of `release/advertised.toml` at that head and
  the base's `[project]` version, and always at `tag`, `release-event` and
  `public-visitor`; a version that cannot be read fails closed. So a release
  PR that also moves `release/advertised.toml` still needs R, and the rule
  cannot re-verify a release before v0.11.0.
- `doctor.py`'s two pin lines are read as text and checked against the
  parsed module, which is never executed: no carriage return or form feed;
  UTF-8 as import reads it, with no other PEP 263 declaration and no
  byte-order mark; each name bound once, by a module-level assignment on its
  own line; no other binding or mention of either name (a `def`, class,
  argument, import alias, `global`, attribute, keyword or string, or
  `import *`); and no dynamic reach into the namespace (`exec`, `eval`,
  `compile`, `globals`, `locals`, `vars`, `setattr`, `delattr`, `__import__`,
  `__dict__`, `importlib` or `builtins`). `src/checkwash/` holds no other
  `doctor` module, such as a `doctor/` package that import would take
  instead. A `doctor.py` that does not parse is refused.
- `doctor`'s previous pin is the announced pin, the trusted ref's
  `ACTION_SHA`, and every `taipei49314/checkwash/action@` reference in
  README.md, in any case and read as its whole token, is exactly that pin, so
  `@<pin>^{}` or `@<pin>-x` fails.
- At `pr` the head is R. Later, the head is a two-parent merge of the base and
  R with R's tree, R is the verified PR head at `main`, and GitHub's own
  commit object lists the parents in that order.
- R has one parent, A, which is the own pin and differs from the previous
  pin. A is clean: its `doctor` holds the previous pin on both lines. From A
  to the head only `src/checkwash/doctor.py` changes, mode 100644, in
  exactly the own line, from the previous pin to A; the diff passes
  `--ignore-submodules=none`, so the checkout's `.gitmodules` cannot hide a
  gitlink change.
- A shallow clone or a missing parent fails closed.

The rule binds the pin text, its single static binding and a single
`doctor` module. `doctor`'s other logic, such as `_ACCEPTED` and the checks
that use it, and code in other modules that could change `doctor` at
import, are the release PR's reviewed content. The ordinary receipt bridge
reads the pin lines the same way.

Users verify the v0.11.0 pin in a clone: `git -C checkwash rev-parse 'v0.11.0^2^1'`
gives A, and `git -C checkwash diff 'v0.11.0^2^1' v0.11.0` shows the one
`doctor` line ([Action reference](../action/README.md#public-pin-and-upgrade)).
Pin updaters that follow the `# v0.11.0` comment, such as Dependabot and
Renovate, will propose the tag's commit, which `doctor` rejects (inferred from
their documentation, not run); Nelson accepted that with documentation
(D-194). For the same reason zizmor's `ref-version-mismatch` audit (1.14.0
and later) can report the README pin's comment, and its pedantic
`stale-action-refs` the untagged commit (inferred, not run); Nelson accepted
that with documentation for 0.11 (D-196).

Scheme S does not change: A, R, the merge commit only, and M with R's tree.
The distributions are still built from M, and the `main`, `tag`,

below, and a tag up to v0.11.x keeps the rule above. No tool accepts either.

- *The tag.* An annotated tag on A whose message holds exactly one line
  `Release-Merge: <M>`, made with the command `tools/own_action_pin.py tag`
  prints and checked before the push by `check --stage tag` (step 5).
- *The release bridge.* At `tag` and later it reads M's and R's commit
  objects from GitHub and requires the tag to peel to A = `M^2^1` and its

- *The collector.* At `tag` and later the local annotated tag must point at

  clean checkout of A with the tag fetched, since
  `tools/verify_published_source.py` requires the source commit to be the
  checked-out one. Preflight checks that checkout, clean at A and holding

  stage steps compare it again after them. Its receipt then proves that the
  tag and A
  agree, no longer that the tag and the build commit M agree: the one-line
  relation of scheme S and the bridge's native reads bind A to M.
- *The verdict gate.* On a tag run, HEAD is M, the tag points at `HEAD^2^1`,

- *A CLI installed from the tag.* It is A's, whose `doctor` holds the

## Before the tag: the fixed-corpus comparison

A standing step since 2026-10-19 (owner ruling 2026-10-19, R29, with R27 and
R3; [#212](https://github.com/taipei49314/checkwash/issues/212)). It runs
once the candidate commit is fixed, before step 5.

- **Sets.** The previous published release (for 0.11.0, v0.10.0,
  `100699796d942af30644738ffbcd1f1c939411c5`) and the candidate each check
  two fixed in-sample sets: the
  Python `standard` set, 300 commits from each of attrs, click, flask, httpx,
  rich and starlette (D-141, arm 1), and the JS/TS set of
  [`benchmarks/javascript-replay/`](../benchmarks/javascript-replay/README.md),
  300 commits from each of six repositories. Each commit is checked against
  its first parent with `check --format json`, once per engine, as every
  JS/TS run so far did
  ([results](../benchmarks/javascript-replay/results.md)).
- **Candidate.** The commit to be tagged, or a commit whose `src/` tree
  differs from it only in the version string in `src/checkwash/__init__.py`
  (step 1), which `check --format json` prints only as
  `run.checkwash_version`, and, from v0.11.0, in `doctor`'s
  `_OWN_ACTION_PIN` line, which `check` never imports (owner ruling
  2026-11-02, D-196). So a candidate frozen before the version bump, or
  before R, still counts. If anything else in `src/` changes after the
  comparison, the comparison runs again.
- **Where.** Current EC POLICY `pju-primary-execution-20261024` (T-610)
  designates LAPTOP-01AGNPJU as the default authorized execution host,
  including this release verification. Preserve this comparison's frozen
  source, sets, individual run approval, isolation and acceptance conditions.
  Record `HUMAN_AUTHORIZED_LOCAL_PJU_NOT_EC_POOL`, actual runtime and original
  receipts. This supersedes the former pool-only and sweep-only exclusions.
  Capable pool evidence retains its actual pool provenance; unexecuted platforms
  remain `NOT_RUN`. The owner confirmed the pool is offline and instructed
  agents to stop connection investigation. [Current policy source](https://github.com/taipei49314/estate-consolidation/blob/103c52abd38eb87c13980aa7cf6f0db4412e53ac/POLICY.md).
- **What goes to the owner.** Every commit whose outcome moves from pass to
  block, from block to pass, or from an analysed verdict to an engine error,
  and every commit the candidate blocks that the previous release could not
  analyse. Each comes with a reading of its change. The tag waits until the
  owner has reviewed the list. There is no rate threshold, so no new block
  reaches a release without the owner seeing it, as in the v0.5.0 tag gate
  (under "The release slot").
- **Recorded only.** An engine error that becomes a pass, an error that
  stays an error, and a verdict that holds. These do not hold the tag.
- **Waiver.** Only a release's own one-time authorization can waive or
  defer this step, and it says so, as v0.8.0's did when the owner chose to
  release first and run the sweeps after publication. No standing waiver
  exists.
- **Record.** The run identities, the list and the owner's review are
  recorded with the release's authorization in this file. The release guide
  states the JS/TS result beside the Python result, labelled in-sample, with
  both engine commits, as counts of commits and never as a false-positive
  rate (SPEC §10.2 rule 1). The JS/TS result is also added to the
  [results record](../benchmarks/javascript-replay/results.md). From
  v0.11.0 they go in the release PR before R is written, or in the step-8
  follow-up (D-196).
- **What it is not.** Both sets are in-sample. The comparison shows what
  changed between two versions on commits the project knows. It is not a
  held-out or adjudicated false-positive rate
  ([known issues](KNOWN-ISSUES-next.md)).

A JS/TS round's pull request states that this step checks its JS/TS
false-positive cost at the next release, instead of citing #212.

## Hosted release verification

Each release gets one verification on GitHub-hosted macOS and Linux runners,
under EC POLICY `checkwash-release-hosted-verification-20261111` and
[D-204](../DECISIONS.md). It has two checkpoints, each dispatched on its
own: `source-at-M` in step 3 and `published-artifacts` in step 7. The
`both` choice, which runs the two in one dispatch, is only for a version
published before the workflow existed (v0.12.0).

On 2026-11-08 Nelson adopted Claude's recommendation of a hosted macOS
check for each release (「macos採用你的建議」) and wrote
「同意每版一次 macOS 驗證，也同意對 v0.12.0 補跑一次；先把設計及 workflow 補完整」
(agreed: one macOS verification per release, and one run for v0.12.0;
complete the design and the workflow first), with the requirements D-204
quotes. On 2026-11-11, after a fresh review of the project, he chose the
option Claude had written as D-甲, one verification on macOS and Linux with
the Action run once the way the README sets it up (「是，D-甲」), answered
eight of the design's nine questions with 「都照建議」 (all as recommended)
and approved the POLICY row with 「照這樣入帳並開始」 (enter it like this
and start). A review before the row was entered found two factual errors
in it, and he approved their correction with 「照兩處更正入帳」 (enter it
with the two corrections). Claude wrote the options, the questions and this
design.

The workflow is `.github/workflows/release-hosted.yml`. The agent releasing
the version dispatches it from main with `gh workflow run` on
LAPTOP-01AGNPJU. It runs only when dispatched, holds `contents: read` only,
and rebuilds none of the published files. Its source and published-file
legs run on `macos-latest` (Apple silicon) and `ubuntu-latest`, each with
Python 3.11, 3.12 and 3.13, and each leg checks that its runner is the
system its label names.

1. **`source-at-M`**, as soon as M is on main and before the tag (step 3).
   It checks out M by its SHA and checks scheme S's shape: M has two
   parents, the second R, which has one parent A; M's tree is R's; only
   `src/checkwash/doctor.py` differs between A and M; M is on main and holds
   the version; a tag already pushed peels to A and names M. Then on each of
   the six legs it runs the whole suite with no selection, the source
   assertion-contract qualification and its inventory, and emits the fixed
   corpus. The six corpus outputs must be byte-identical and, when the
   release has a six-leg batch, equal that batch's SHA256, which the
   dispatch carries. With the batch's Windows legs, every pair of operating
   system and Python then has an output with the same hash; that is still
   not the one-run nine-leg comparison.

   In the same checkpoint, on `ubuntu-latest` with Python 3.12, the runner
   executes the composite Action at A on M's release range, from M's first
   parent to M, with the Action's default inputs and the base given. It must
   pass with exit 0, and its receipt must name that range, the version and
   the default `fail-on`, with an engine whose source digest equals that of
   A's `src/checkwash`. The Action builds and installs its engine from A's
   source and fetches its build backend from PyPI, as it does for any user.
   Five things differ from the README's job:
   - The composite is A's own `action/` directory, checked out by SHA and
     used by a local path, because a `uses:` value must be a literal and
     cannot take an expression. GitHub's resolution of
     `taipei49314/checkwash/action@<A>` is not exercised.
   - That checkout sits in a subdirectory of the subject's workspace, the
     checkout of M.
   - The run is dispatched, not triggered by a pull request, so the base is
     given.
   - The engine judges allowlist expiry as on M's commit date
     (`CHECKWASH_TODAY`), as the published-file checks do, so a later run
     for the same release cannot change the verdict.
   - The range is expected to pass, so the run does not show the Action
     blocking a change.
2. **`published-artifacts`**, once `publish-assets` has attached the
   Release's files and before Nelson is asked to approve the `pypi`
   deployment (step 7). The dispatch carries the Release ID and the three
   files' SHA256 values from the release record: the `publish-assets`
   readback (`release-assets.json`), which equals the release-event
   receipt's artifact table. The run reads the Release by its ID and
   requires exactly the wheel, the sdist and the pyz, uploaded at their
   canonical URLs, with GitHub's digests present and equal to those values.
   When the publication record or PyPI already has the version, their
   values must agree too, and the record's row for each file must name its
   SHA256. Then on each of the six legs it downloads the three files from
   their canonical URLs and checks their SHA256 again, installs the wheel
   with `--no-deps --no-index` into a fresh venv, runs the installed CLI and

**Records.** The run ID and attempt; for each leg the runner label, image
and version, the operating system version and architecture, and the
Python; M, R, A and the tag object; each leg's test cases, subtests and
skips with their reasons; the conclusion of each step; each qualification
and inventory result; the corpus SHA256s; the Action's receipt; and each

**What it is not.** It is hosted evidence beside the PJU receipts: not a
receipt and not a branch required status. It replaces no PJU stage,
required check or approval of Nelson's, and not the release-event
missing-platform acceptance, which still lists Linux and macOS because the
receipts hold neither. A wheel or pyz rebuilt from M is not the published

called a rebuilt-artifact verification; separate pyz builds of one tree
differed in their bytes in every release from v0.10.0 to v0.12.0
([pyz reproducibility](#pyz-reproducibility)).

## Why neither phase gets an escape hatch

The historical `test_pinned_tag_ships_the_current_source` existed because
**v0.1.0 pointed two fixes behind main**: people installed the pre-fix engine
while reading post-fix claims. On 2026-08-08 a missing-tag early return was
added and removed the same day. Passing because the subject is absent remains
prohibited. These historical facts and failed receipts are unchanged.

The replacement preserves that responsibility at the phase that can actually
prove it. Ordinary candidate CI runs the same validator against controlled
positive/negative Git identities and verifies the already-advertised public
release. Tag and release jobs require the real new public identity. No missing
subject becomes a skip-success, and no new capability is advertised as shipped
merely because the candidate passes. The prior policy of treating routine
candidate/tag divergence as an expected development failure is superseded by
this explicit separation; no test selection or `continue-on-error` hides it.

The verdict gate continues to require success on the release PR's final head,
then the exact release commit on main, then that same commit at the tag stage:
up to v0.11.x the commit the public tag points to, and from v0.12.0 the
release merge whose Action commit the tag points to and whose id its message
gives (D-200). A failed, cancelled or missing run stops publication. A BLOCK-to-PASS still
requires a repair or the maintainer's recorded acceptance; this phase change
supplies no such acceptance.

## What ships with a release

The PJU release collector builds these from each stage's head, the release
pull request's last commit R at `pr` and then the release merge M, never
from the commit a v0.12.0 or later tag points to, and refuses if the version
and the tag disagree. The `release` workflow's `publish-assets` job uploads
the receipt's verified files to the published Release:

- `checkwash-X.Y.Z-py3-none-any.whl` and the sdist — installed into fresh
  venvs by the collector's visitors, which allow no installed distribution

- `checkwash.pyz` — the single-file build, gated by `tests/test_zipapp.py`

### Assertion capability qualification

Before uploading release assets or publishing to PyPI, the release chain
requires the receipt's runs of `tools/qualify_assertions.py` on the source,
the actual built zipapp and the wheel installed into a fresh venv. All three
execute the same owned
assertion support contract in `tests/data/javascript_assertion_support.json`
and the separate `javascript_foundation_mutations.json` supplement through
real Git commits and the CLI. Each loss must report the expected
rule, severity, path, JSON verdict and process exit; preserving controls must
pass without findings. Clean ranges and invalid refs check exits 0 and 2.
These are bounded syntax and mutation checks, not a general false-positive
or adversarial detection-rate estimate.

The deterministic JSON receipts record the suite digest, engine source
commit, source package digest, whether package sources were dirty, artifact
SHA256, reported version and every case result. Qualification checks the
archive's package bytes against the source tree and, for wheels, also checks
the isolated venv's loaded package. A different artifact or loaded package
fails even if its version string matches. The candidate source, commit and
artifact must remain unchanged during the run. No receipt is stored inside
`dist/`, so PyPI receives only its supported distribution files.

The `assertion qualification` workflow also installs the exact SHA recommended
for the Action in the README and runs the same suite. This is explicitly an
**Action-pinned engine** check, not qualification of the composite Action's
wiring. Its receipt names that engine's own source commit and version. It is
a separate job because the recommended pin can trail the candidate on `main`
and so expose real capability gaps. Until 2026-10-14 the pin also lagged one
release behind (for example, the v0.5.0 pin lacked the v0.6.0 work on the
reports and rulings that followed #172–#181); it now advances to each newly
verified release. Its actual result is measured independently. The job
remains visibly failed when cases fail; no expected-failure
or `continue-on-error` waiver turns those gaps green. The recommended pin
and release authorization remain governed by the existing release process.

For local source qualification:

```bash
python tools/qualify_assertions.py --distribution source --output work/assertion-source.json
```

For a built wheel installed into a fresh venv, use the venv's absolute Python
path so neither an editable checkout nor `PYTHONPATH` can supply its engine:

```bash
python tools/qualify_assertions.py --distribution wheel --artifact dist/checkwash-X.Y.Z-py3-none-any.whl --output work/assertion-wheel.json -- /absolute/fresh/bin/python -I -m checkwash
python tools/qualify_assertions.py --distribution pyz --artifact dist/checkwash.pyz --output work/assertion-pyz.json
```

Fixture analysis is zero-network and never executes fixture tests. The
collector uses build/install tooling separately to create the candidate
distributions.

### pyz reproducibility

The collector builds the zipapp with:

```bash
python -m zipapp src -m "checkwash.zipapp_entry:run" -o dist/checkwash.pyz -c
```

That is **source-reproducible** on the same CPython minor: same `src/`
tree, same `-m` entry, compressed. It is **not** bit-identical across
Python versions or zip implementations. Visitors should treat the
GitHub release asset as the artifact and verify it by running
`python checkwash.pyz --version` and `python checkwash.pyz demo`.
`tests/test_zipapp.py`, in every receipt's full suite, is the gate that the
recipe still works; the Release asset is what people download.

Builds at different times also differ in the zip entries' timestamps: in
each release from v0.10.0 to v0.12.0 the stages' pyz files held the same
members with identical contents and different bytes (for example, the
[0.12.0 record](releases/v0.12.0-publication-verification.md)).
So a pyz rebuilt from M is not the published file unless its bytes are shown
equal, and checking one is a rebuilt-artifact verification. The [hosted
release verification](#hosted-release-verification) checks the downloaded
Release asset itself.

Workflow `uses:` of other repositories' actions are hash-pinned (T2.6); the
hosted release verification's one local `uses:` runs the checkout of A
that it binds by SHA. `contents: write` exists only
on the `publish-assets` job, only to attach assets to an already-published
release. PyPI uses OIDC (`id-token: write`) and no stored token.

## PyPI

Gated on a repository variable, on purpose — and **the gate is open**:
`PYPI_ENABLED` has been `true` since 2026-09-01, so every GitHub Release
since 0.2.1 has also published to PyPI (`pipx install checkwash`). A published
release proceeds to PyPI once the maintainer approves the `pypi` deployment,
and the wheel and sdist on PyPI are the same
bytes the `build` job attached to the release (checked on 0.2.11,
2026-09-02). That approval was added on 2026-10-14 (step 7). The `pypi` job publishes
through trusted publishing, so no token is stored anywhere by anyone. The
approval is a gate only if the PyPI trusted publisher names the `pypi`
environment: the `release` event runs the `release.yml` of the tagged
commit, so without that binding a tag on a commit whose workflow omits the
environment could still upload. The three steps
that opened the gate, all the maintainer's:

1. Register checkwash as a trusted publisher on PyPI for this repository and
   the `release` workflow.
2. Set the repository variable `PYPI_ENABLED` to `true`.
3. Keep the `pypi` environment for its deployment protection rules. Since
   2026-10-14 that rule is a required reviewer: the maintainer
   (`taipei49314`), self-review allowed, no administrator bypass.

Without (2) the job is skipped and releases are GitHub-only. To go back to
GitHub-only releases, unset the variable; nothing else has to change.

**This paragraph used to say something false, and it is worth knowing why.**
It claimed the job was gated behind an environment "that does not exist until
a human creates it". GitHub creates an environment automatically the first
time a job references one, so the gate was open from the moment it was
written. Nobody noticed because the release workflow had never run: it was
added in v0.1.12, whose release predated it. On v0.1.13 it ran for the first
time, published all three assets correctly, and then failed on a trusted
publisher that does not exist — turning a clean release red.

The gate is a repository variable now, because nothing auto-creates one, and
`tests/test_packaging.py::test_pypi_job_is_gated_on_something_that_is_not_auto_created`
fails if it ever goes back to being gated by `environment:` alone. D-032 has
the full account.

on subsequent uploads ([PyPI JSON API](https://docs.pypi.org/api/json/)). A
description correction therefore needs a new version through the existing
release process. Do not delete, replace or re-upload an existing release to
rewrite its description. Until the next release, link readers to the current
GitHub README and retain the old release's actual status in the launch notes.

## After the release

- Check CI is green on the tag, not just on main.
- Open the verdict gate's separate rotation PR (step 9); until it merges, the gate
  still compares against the release before this one.
- `benchmarks/RESULTS.md` and `benchmarks/FAILURES.md` are generated. If the
  round changed anything they summarise, regenerate and commit them —
  `tests/test_state_claims.py` fails if they drift.
- If the round changed detector behaviour, the corpus sweep is not optional.
  If it changed only I/O or documentation, say which targeted checks stood in
  for it, in `DECISIONS.md`, by name.
- Cut the decision log (owner ruling 2026-10-20, round 7 H5). At the
  release's publication, or as soon as `DECISIONS.md` passes 800,000 bytes,
  whichever comes first, the entries up to and including the newest release
  entry move to the next archive, `DECISIONS-archive-<k>.md`: a prefix of the
  file, line 1 retitled and line 2 one unwrapped line, nothing else changed, so
  every line keeps its number. `DECISIONS.md`'s pointer paragraph gains one
  sentence for it. Under the size trigger the owner names the boundary.
  Archived entries are not edited again; a correction is a new entry that
  cites the old one. `DECISIONS-archive-1.md` holds D-001 to D-140.
